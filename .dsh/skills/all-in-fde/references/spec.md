# 校准（spec）

把 brief 摊成需求采集表，人审定后出 **PRD**，再从 PRD 派生出按模块命名的 **spec**。这是全流程的事实层——后面的票、代码、验收都从 PRD + spec 取，不再回看采集表。

## 什么时候用

采集表已生成（从 intake.md 产出），但还没有 PRD / 原型 / spec。

## 12 步流程中的位置

```
6. AI 生成采集表       ← intake.md
7. 人审定采集表        ← §阶段A
8. AI 生成 PRD         ← §阶段B
9. 人审定 PRD          ← §阶段B
10. AI 生成原型 → 人审定 ← §阶段B
11. AI 生成 spec → 人审定 ← §阶段C
12. 封版               ← §阶段D
```

**每个人审触点都是阻断性的**：未审定不许进下一步。

## 三级真源与封版

```
采集表（人审定）→ prd.md 或 prd/<章节>.md → spec/<module>.md
                                            ↓
                                      E2.5 封版门禁（阻断）
                                            ↓
                                      切片（分工依据是 PRD+spec）
```

- **采集表**是输入，不是真源。它只负责把人说的话结构化，审定后即冻结。
- **PRD** 是第一级真源。章节结构参考但不照搬采集表；过大时拆成 `prd/` 目录下多文件。
- **spec** 是第二级真源。每个业务模块一份 `spec/<module>.md`，从 PRD 派生，是切片的直接依据。
- **封版**：PRD + 所有 spec 都标记 `status: sealed` 后才能进切片。未封版就切片 = 流程错误。

## 怎么做

### 阶段 A：人审定采集表

1. **填表**：按 `assets/需求采集表-空白模板.xlsx` 的 16 张表填。轻量档只填 S0/S1/S3/S5/S7/S11，其余在 S15 记「本档不适用 + 理由」。
2. **填表铁律**：
   - S0 原文一字不改；客户没说的写「待确认」，AI 推断只进 S13「AI建议方案」，不许写进事实列。
   - 编号发布后不复用（`REQ-`、`AC-`、`BR-`、`EB-`、`F-`、`E`、`ST-`）。
   - 每行能回指来源；指不到就是编的。
   - AC 必须带数据断言（金额到分、汇总=明细合计、状态字段值），只写「操作成功」的 AC 不算数。
3. **人审五页**：只请人看 S0 原话、S3 角色、S5 主链、S7 页面、S13 疑问，出决策卡（≤3 项/轮）。审定痕迹 = 五页「客户核验」列全为已核验。**未审定不许进阶段 B**。
4. **草稿**：成稿前的中间稿放 `.fde-tmp/drafts/`，成稿才写进正式目录。

### 阶段 B：出 PRD → 人审定 → 出原型 → 人审定

5. **写 PRD**：以审定后的采集表为输入，产出 PRD。PRD 章节结构**参考但不照搬**采集表的 S1–S15 顺序，应按业务逻辑组织。推荐结构：

   ```text
   # PRD：<项目名>
   ## 1. 概述（背景、目标、范围、不做什么）        ← 参考 S0/S1/S2
   ## 2. 角色与权限                                ← 参考 S3/S4
   ## 3. 业务流程与状态机                          ← 参考 S5/S6
   ## 4. 页面与交互                                ← 参考 S7/S8
   ## 5. 数据模型与契约                            ← 参考 S7/S8/S9
   ## 6. 接口规格                                  ← 参考 S10/S11
   ## 7. 非功能需求                                ← 参考 S12
   ## 8. 验收标准                                  ← 参考 S11（AC- 编号）
   ## 9. 约束与假设                                ← 参考 S13/S14/S15
   ## 附录：编号追溯矩阵                           ← REQ-/AC- 与采集表行号对照
   ```

   这不是死模板——项目简单时可合并章节，复杂时可加子章节。**核心原则：PRD 是给人读的业务文档，不是采集表的转写**。

6. **PRD 拆分规则**：
   - **单文件**：PRD ≤ 3000 行时，写 `.fde/prd.md`。
   - **多文件**：PRD > 3000 行或章节独立性强时，建 `.fde/prd/` 目录，按章节拆：
     ```text
     .fde/prd/
     ├── 00-overview.md          # 概述
     ├── 01-roles.md             # 角色与权限
     ├── 02-flows.md             # 业务流程
     ├── 03-pages.md             # 页面与交互
     ├── 04-data-model.md        # 数据模型
     ├── 05-api.md               # 接口规格
     ├── 06-nfr.md               # 非功能需求
     ├── 07-acceptance.md        # 验收标准
     └── index.md                # 目录索引 + 元信息
     ```
   - 多文件时必须有 `index.md`，列出所有章节文件、版本、封版状态。
   - 不论单文件还是多文件，PRD 顶部必须有元信息块：
     ```yaml
     ---
     version: "1.0"
     status: draft | review | sealed
     sealed_at: null | "2026-11-20T10:00:00+08:00"
     sealed_by: "张三"
     source: "采集表 v1.0，审定日期 2026-11-19"
     ---
     ```

7. **PRD 与采集表的关系**：PRD 正文只引用编号（`REQ-C01`、`AC-C01`），不再抄字段表。需要回溯时用附录的追溯矩阵。PRD 与采集表冲突时，**以采集表审定版为准**（采集表是人审过的，PRD 是 AI 写的）。

8. **出原型**（UI 项目）：每个页面顶部写注释 `<!-- 页面ID: xxx | 来源: PRD §4 / S7 rN -->`。字段、按钮、空态与 PRD 逐项对应，原型不发明字段。

9. **人审定 PRD**：将 PRD 全文（或 index.md + 各章节摘要）展示给人，请人确认：
   - 业务流程是否正确完整
   - 验收标准是否可执行
   - 编号追溯矩阵是否与采集表对齐
   - 有无遗漏或过度设计
   
   **未审定不许出原型**。审定意见回写到 PRD 并更新版本号。

10. **人审定原型**（UI 项目）：将原型展示给人，请人确认：
    - 页面布局与交互是否符合预期
    - 字段、按钮、空态是否与 PRD 一致
    - 有无遗漏页面或流程
    
    **未审定不许进阶段 C**。审定意见回写到原型和 PRD。非 UI 项目跳过此步。

### 阶段 C：出 spec → 人审定

11. **识别模块**：从 PRD 中提取业务模块列表。每个模块对应一个独立的业务域（合同、用户、审批、通知……），不是技术分层（前端/后端/数据库）。模块划分依据：
   - PRD 里的业务流程边界
   - 数据模型的聚合根
   - 权限域的独立性
   - 可独立演示的最小单元

12. **写 spec**：每个模块一份 `.fde/spec/<module>.md`，文件名 = 模块英文标识（kebab-case）。推荐结构：

    ```text
    # Spec：<模块中文名>（<module>）
    ## 元信息
    - PRD 来源：§3.2 / §6.1
    - REQ：REQ-C01, REQ-C02
    - AC：AC-C01, AC-C02, AC-C03
    - 依赖模块：user, auth
    - status: draft | sealed
    
    ## 1. 业务规则
    （从 PRD 派生，细化到可实现粒度；含状态机、不变量、边界条件）
    
    ## 2. 数据契约
    （Zod schema 草案、字段约束、枚举值；与 packages/shared 对齐）
    
    ## 3. 接口契约
    （路由、请求/响应 schema、错误码；与 apps/api 对齐）
    
    ## 4. 页面与交互
    （页面 ID、组件树、表单校验规则；与 apps/web 对齐）
    
    ## 5. 验收谓词
    （从 PRD AC- 派生，每条含 Given/When/Then + 数据断言）
    
    ## 6. 技术备注
    （实现约束、性能要求、与现有模块的集成点）
    ```

13. **spec 与 PRD 的关系**：spec 是 PRD 的**模块级投影**。PRD 说「合同审批需要三级审核」，spec/contract.md 把它细化成状态机图、API 签名、前端组件树、验收谓词。spec 不发明 PRD 没有的需求；发现缺口时回写 PRD 并重新封版。

14. **人审定 spec**：将所有 `spec/<module>.md` 展示给人（或逐个展示），请人确认：
    - 业务规则是否细化到位
    - 数据契约是否与 PRD 一致
    - 接口契约是否可实现
    - 验收谓词是否可执行
    
    **未审定不许封版**。审定意见回写到 spec 并更新版本。

15. **回写**：生成 PRD/spec 中发现的缺口记采集表 S15，新问题记 S13，人拍板记 S14 并回写受影响行。回写后 PRD/spec 需重新审定。

### 阶段 D：封版

16. **封版检查**：
    - PRD 元信息 `status: sealed`，`sealed_at` 与 `sealed_by` 非空；
    - 所有 `spec/<module>.md` 元信息 `status: sealed`；
    - 每个 spec 的 `REQ-` / `AC-` 都能在 PRD 里找到对应条目（追溯矩阵非空）；
    - 采集表 S15 无未覆盖项。

17. **写证据**：`evidence/E2.5-sealed.json`，记录封版时间、封版人、PRD 版本、spec 清单与版本号。这是 E2.5 门禁的执行体。

## 什么算完（E2 + E2.5）

### E2 规格（记录门，不阻断）

四项都是「列集合、求差集」，差集为空才算过：

- 采集表齐不齐（按档；轻量档缺的表必须在 S15 有「不适用 + 理由」）；
- S15 每行「覆盖结论」无未覆盖；
- PRD 全文的编号与表内编号求差，差集为空；
- 原型页面 ID 与 PRD §4 页面 ID 求差，差集为空。

### E2.5 封版（阻断门，v0.5.0 新增）

- PRD `status: sealed`，`sealed_at` 与 `sealed_by` 非空；
- 所有 spec `status: sealed`；
- 每个 spec 的 REQ-/AC- 在 PRD 中有对应条目；
- `evidence/E2.5-sealed.json` 存在且 `mode: PASS`。

**未通过 E2.5 不许进切片。**

## 常见错

- **AI 把推断写进事实列**：推断只进 S13，事实列留「待确认」。
- **表填完没人审就生成 PRD**：A1 的出口判据是审定痕迹，不是「表生成出来了」。
- **PRD 照搬采集表结构**：PRD 是按业务逻辑组织的文档，不是 S1–S15 的转写。
- **PRD 与表各写一套**：PRD 只引用编号，再抄一遍字段表就是第二份真相。
- **跳过 spec 直接切片**：spec 是切片的直接依据；没有 spec 就切片，等于凭感觉分工。
- **spec 发明了 PRD 没有的需求**：spec 是 PRD 的投影，不是二次创作。发现缺口要回写 PRD 并重新审定。
- **没封版就切片**：E2.5 是阻断门，未封版的 PRD/spec 还在变，切出来的票随时作废。
- **跳过人审直接进下一步**：采集表/PRD/原型/spec 每一步都有人审触点，未审定不许往下走。这是 v0.6.0 的硬规则。
- **原型照搬了需求稿的 DOM 和色值**：只取字段与流程语义，UI 走设计系统的语义 token。
