# 理解与提案（understand）

在收活之后、填采集表之前，AI 与人进行**两轮卡片交互**：第一轮理解+提问，第二轮粗提案。目的是让人快速确认 AI 的理解是否正确、方案是否合理——**先共脑，再填表**。

## 什么时候用

用户给了一段需求描述（口头/文字/文档/文件夹），Router 已初步解析但尚未产出 brief.md。

## 12 步全流程定位

```
1. 人梳理需求文件夹
2. AI 理解 + 提问（理解卡 HTML / DSH 交互选择题）  ← 本文件 §阶段A
3. 人回复                                            ← 本文件 §阶段A
4. AI 粗提案（提案卡 HTML）                          ← 本文件 §阶段B
5. 人审定                                            ← 本文件 §阶段B
6. AI 生成采集表                                     ← intake.md
7. 人审定采集表                                      ← spec.md §阶段A
8. AI 生成 PRD                                       ← spec.md §阶段B
9. 人审定 PRD                                        ← spec.md §阶段B
10. AI 生成原型 → 人审定                              ← spec.md §阶段B
11. AI 生成 spec → 人审定                             ← spec.md §阶段C
12. 封版 → 切片 → 起架 → 逐单 → 验收 → 交付           ← 后续流程
```

## 阶段 A：理解 + 提问

### 做什么

AI 解析用户输入（含需求文件夹里的文档），生成**理解卡**，包含：
- 核心理解（一句话目标 + 标签 + 摘要）
- 关键疑问（3–7 条，每条带 AI 临时假设 + 可选答案）
- 范围边界初判（做什么 / 不做什么）
- 利益相关者初判

### 呈现方式（二选一或组合）

1. **HTML 理解卡**：调用 `scripts/gen-understand-card.mjs`，输出单文件 HTML，用 `present` 展示。适合内容多、需要视觉层级的场景。
2. **DSH 交互选择题**：用 `ask_user_question` 工具，把关键疑问做成可点选的选择题。适合疑问少、需要快速回答的场景。

两种方式可以组合：先用 HTML 卡片展示全貌，再用交互选择题收集关键决策。

### 提问排期纪律（阶段 A/B 通用）

疑问不是平铺的一张清单，是一棵树：有些疑问的答案决定另一些疑问能不能问。按层分批问：

1. **一轮问完当前能问的全部疑问**。依赖未回答疑问的后续问题留到下一轮，不许靠猜测答案提前问。
2. **每条疑问必须带推荐假设**——这条已有。措辞让人回答「是」即接受推荐，不同意才需要打字改。
3. **能自己查到的不许问人**。事实性问题（代码现状、环境、文档里写了的东西）派只读子代理去查；只有需要人拍板的决策才进疑问清单。查证中的问题属于下一轮，不阻塞本轮其余疑问。
4. **出口判据收敛于 S13**：疑问树问到「采集表 S13 没有待确认项」即可停，不追求穷尽整棵决策树。用户说「够了，直接出卡」视为强制收敛，剩余假设如实记入 S13。

常见错补充：
- **一次只问一个问题来回十几轮**：零散打断人，且每轮都在重付上下文成本。一轮一批。
- **问人自己能查的事**：把查证的活推给人，是 AI 失职，不是谨慎。
- **前置未决就把下游问题抛出去**：得到的回答建立在猜测之上，返工比多等一轮更贵。

### 人回复

人可以：
- 在 HTML 卡片上点选选项（如果嵌入了表单）
- 直接回复文字修改意见
- 回答 DSH 交互选择题
- 说"确认"进入阶段 B
- 说"重做"让 AI 重新解析

AI 收到反馈后更新理解卡并重发，直到人明确确认。

### 什么算完（阶段 A）

- **plan 已执行**：`node <token-budget>/scripts/plan.mjs --task "<用户原话>" --json` 退出 0，返回的 `type`/`effort`/`peak`/`suggestDefer` 记入 `.fde/brief.md` 元信息区。没跑 plan 不许出理解卡。
- 理解卡已生成并展示给人；
- 所有关键疑问已得到人的回复（选择/文字/确认）；
- 人明确说"确认"或等效表达。

## 阶段 B：粗提案

### 做什么

基于阶段 A 确认的理解，AI 生成**提案卡**，包含：
- 推荐技术栈（从脚手架坐标推断，或给出备选及理由）
- 模块划分草图（业务模块列表 + 依赖关系文字描述）
- 关键实现路径（1–3 条核心链路）
- 风险点与缓解策略（红色标注高风险项）
- 报价参考（**只方便人报价，不是 AI 工时**）：按人工产能基线换算人天——**1 人天 = 10 个简单 CRUD 模块，或 3 个复杂模块**。简单 = 单表增删改查 + 列表页；复杂 = 含状态机 / 审批流 / 跨模块联动 / 统计报表。人天 = 简单个数 × 0.1 + 复杂个数 ÷ 3（向上取整到 0.5 天）。卡上必须标注「人工产能口径，仅供报价」。**AI 实现不按此估时、也不按此排期**——切片与派发只看票依赖与上下文容量。
- 开放问题（仍需人决策的技术选型点）

### 呈现方式

**必须用 HTML 提案卡**：复用 `scripts/gen-understand-card.mjs`（提案内容填 JSON 的 `solution`/`estimate` 字段，estimate 写报价参考），或按同款 liquid-glass 风格手写单文件 HTML。提案内容比理解卡更复杂，需要更强的视觉层级区分"已确定 / 待决策 / 风险"。

### 人审定

人审阅提案卡后可以：
- 说"通过"→ 进入采集表阶段
- 指出具体修改点 → AI 更新提案卡重发
- 提出新的技术约束 → AI 重新评估方案
- 说"换方案"→ AI 给出备选方案

### 什么算完（阶段 B）

- 提案卡已生成并展示给人；
- 人明确审定通过；
- 技术方案方向已锁定（后续采集表和 PRD 以此为基准）。

## 常见错

- **把理解卡做成 PRD 预览版**：理解卡是"AI 的理解"，不是"最终规格"。不要写字段、不要写接口签名、不要写状态机细节。
- **把提案卡做成详细设计文档**：提案卡是"方向性方案"，不是"实施规格"。模块划分到业务域级别就够了，不要画架构图、不要写代码片段。
- **疑问太少或太多**：<3 条说明 AI 没认真想，>7 条说明需求不成熟。3–7 条是健康区间。
- **跳过理解卡直接出提案**：必须先确认理解，再出提案。否则提案可能建立在错误理解上。
- **跳过提案直接填采集表**：必须先锁定技术方案方向，再填采集表。否则采集表里的技术约束列会反复改。
- **理解卡/提案卡落盘为证据**：它们不是 E0–E7 的任何一项。确认后内容进 brief/采集表即可，HTML 文件留在 `.fde-tmp/` 供回溯。
- **用 Markdown 代替 HTML**：Markdown 在聊天窗口里没有视觉层级，无法区分主次。必须用 HTML + `present`。
- **拿报价人天给 AI 排期**：人天是人工产能口径（1 人天 = 10 简单 CRUD 或 3 复杂），只供人换算报价；AI 实现速度与它无关，排期只看票依赖与串并，不需要也不许按人天估 AI 工时。
- **阶段 A 和阶段 B 合并成一张卡**：理解和提案是两个不同的认知层次，合并会让人难以聚焦反馈。分开两张卡，每张卡的反馈目标明确。
