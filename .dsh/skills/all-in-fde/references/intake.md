# 收活·出采集表（intake）

从已审定的提案 + 已确认的理解中，生成需求采集表。**本步前提是提案已审定**——如果还没有理解卡或提案，先走 `references/understand.md`。

## 什么时候用

提案已审定，但还没有采集表。

## 怎么做

1. **从提案和理解中提取**：
   - 理解卡第1区（核心理解）→ 采集表 S0 原文 + S1 项目背景
   - 理解卡第5区（利益相关者）→ S3 角色
   - 提案卡的模块划分 → S7 页面/功能列表的骨架
   - 提案卡的技术栈 → S9 技术约束
   - 理解卡第4区（范围边界）→ S2 范围 + S15 不适用项
2. **用户原话一字不改贴进 S0**。附 PRD/原型/截图时，登记文件名与存放位置到 S0。
3. **填表铁律**（同 spec.md §阶段A）：
   - S0 原文一字不改；客户没说的写「待确认」，AI 推断只进 S13。
   - 编号发布后不复用。
   - 每行能回指来源。
   - AC 必须带数据断言。
4. **写 `.fde/brief.md`**（如尚未生成）：五节从理解卡+提案沉淀，每节 1–3 行，不许写字段。

## 什么算完

- 采集表已生成（按档填完，轻量档缺的表在 S15 记理由）；
- brief.md 五节齐全；
- S0 至少一条原文，且是用户原话。

## 常见错

- **跳过理解/提案直接填表**：采集表的内容应来自已确认的理解和已审定的提案，不是 AI 凭空填的。
- **把提案的技术细节抄进采集表**：采集表是需求事实层，技术方案在提案卡和后续 spec 里。
- **S0 润色了用户原话**：S0 必须是原话，AI 的理解进 brief，两者分开。
