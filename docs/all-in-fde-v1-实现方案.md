# all-in-fde v1 技能实现方案

> 与《all-in-fde 方案 v0.3》的分工：v0.3 定「做什么、为什么」，本文定「写成什么、谁来执行、怎么验」。
>
> 借鉴来源：一份真实多端项目的开发任务拆解手册（波次 / 节拍 / 串并 / 三阶段勾选 / 四拍节奏），以及它的 E2E 编写方法（PRD 驱动四步法、覆盖矩阵、阻塞场景清单）。内部出处见 `archive/notes/调研出处.md`。

---

## 0 一页纸

**v1 交付什么**

1. 一个入口技能 `all-in-fde`（`SKILL.md` ≤200 行）
2. 七份 reference（收活 / 校准 / 切片 / 起架 / 逐单 / 验收 / 交付）
3. 一套模板资产（需求采集表 xlsx + 生成器），随技能分发
4. 六个脚本（净化、E0 自检、链接检查、seed、E2E 跑批、证据校验）
5. 一套评测集（触发正负例 + 交付任务集 + A/B 对照）

**三种执行者 + 一个人**

| 角色 | 谁 | 职责 | 上下文 |
| --- | --- | --- | --- |
| Router | 入口技能所在会话 | 拆分、派发、排期、收口；不实现 | 常驻 |
| Worker | `fde-逐单` 子代理 | 一票一代理：实现 + 自测 + 交证据 | 干净 |
| QA | `fde-verify` 子代理 | 独立复核 + E2E + 冷启动 | 干净 |
| 人 | 业务方 | 拍板、走查、封票 | —— |

**五个机制**：票（派工凭据）、波次节拍（排期语言）、三阶段勾选（越权边界）、三层测试（自测证据）、覆盖矩阵（测全了没有）。

## 3 七份 reference 大纲

| 文件 | 输入 | 核心步骤 | 出口判据 | 产物 |
| --- | --- | --- | --- | --- |
| `intake.md` | 客户一段话、附件 | 三问（给谁用、输入输出、不做什么）；原文进 S0 | brief 五节齐、S0 至少一条 | `brief.md`、S0 行 |
| `spec.md` | brief + 素材 | 填 16 张表 → 人审五页 → 出 PRD 分卷 → 出原型 | 表无空表、S15 无缺口、编号可回溯 | 采集表 v1.0、PRD、原型 |
| `slice.md` | 采集表 + PRD | 按 S7 页面分组 → 定轨道 → 排依赖 → 分波次 → 写票 | 每票一上下文可完成、可演示、依赖无环 | `tickets/*.md` |
| `scaffold.md` | 项目名、端清单 | 脚手架生成 → 起服务 → 跑空门禁 | 空项目 `check` 绿、端口不漂 | 可启动仓库 |
| `implement.md` | 一张票 | 读回执 → 读 spec → 加载 ponytail → 红绿 → 自测 → 写证据 | 验收谓词逐条有证据、门禁绿、非恒真 | diff + `E5-*.json` |
| `verify.md` | 全部票 + 证据 | 独立复核 → 冷启动 → E2E 真实模式 → 验收卡 | 四步全过、验收卡上无「有问题」 | `E6-*.json` |
| `delivery.md` | 证据汇总 | 交付三件套 → 差异清单 → retro | 干净目录可起、可回滚 | README、retro |

每份 reference 统一四段：**什么时候用 / 怎么做（编号步骤）/ 什么算完 / 常见错**。第三段必须可判定，第四段每条对应一个假绿判例。

## 4 票：切分与派发

### 4.0 票是什么：两份来源的融合

一眼看是两个东西，其实是同一个东西的两面：

- **mattpocock 的票**回答「怎么切」：竖切、做完能演示、一次上下文装得下、写清被谁阻塞。
- **实例的领卡**回答「怎么派、怎么收」：轨道、波次、依赖、生成命令、Spec 位置、三阶段勾选、交付回执。

冲突不在概念，在关注点。融合规则：

| 维度 | mattpocock 的票 | 实例的领卡 | 融合后（票） |
| --- | --- | --- | --- |
| 切法 | 三条判据（竖切、可演示、一上下文） | 不规定 | 票必须先过三条切法判据，过不了的退回重切 |
| 依赖 | blocking edges | 硬依赖列 + 节拍串并 | **两列分开**：`阻塞` 管能不能开，`串并` 管怎么开 |
| 编号 | slug，无序号 | `W1-T03` | 稳定票号 + slug 标题 |
| 验收 | 票内写 AC | 引用 S11 的 AC | 引用 AC 编号 + 3–5 条谓词，不复制全文 |
| 状态 | 待开 / 可开 / 完成 | 三阶段勾选 | 三段签名；done 由证据推导，不手写 |
| 派工信息 | 无 | 轨道、命令、Spec 路径、回执 | 原样保留，作为票的正文 |
| 谁能勾 | 无 | AI 只勾① | 保留：AI 只勾「首轮实现」 |

一句话：**票 = 切法（来自票）+ 派工信息（来自领卡）+ 证据判据（来自本方案）**。名字取「票」，因为它的三个动作——可认领、可阻塞、可交接——正好是这三份来源共同要的。

### 4.1 票字段

沿用实例的领卡结构，砍掉与单人交付无关的项：

| 字段 | 说明 | 例 |
| --- | --- | --- |
| 票号 | `W{n}-T{nn}`；≤5 张票的项目直接 `T-01` | `W1-T03` |
| 标题 | 用户视角一句话 | 合同审批生效 |
| 轨道 | `Base` 底座 / `Module` 业务 / `QA` 验收 | `Module` |
| 硬依赖 | 只写真正阻塞的票号 | `W1-T01` |
| 节拍 | `1️⃣` `2️⃣` `3️⃣` 同波次可启动顺序 | `2️⃣` |
| 串并 | `🔗串联` / `🔀并行` / `🚪汇合` | `🔀并行` |
| 挂 REQ | 采集表 S7 的 REQ 编号 | `REQ-C01` |
| 验收 | S11 的 AC 编号 | `AC-C01/C02` |
| Spec | 规格文件路径加小节 | `docs/specs/contract.md#审批` |
| 命令 | 生成命令或入口 | `gen:module --name contract` |
| 三阶段 | `① AI 首轮` `② 人走查` `③ QA 封票` | 三个复选框 |
| 回执 | Spec 路径、迁移号、接口/表摘要、下游提醒 | 票末一段 |

### 4.2 波次 · 节拍 · 串并

沿用的符号与含义：

- **波次（Wave）**：一组必须一起想清楚的票。Wave 0 是底座（账号、状态机、编号、共享组件），之后按业务域分。
- **节拍 1️⃣2️⃣3️⃣**：同一波次里能先后启动的顺序，不是甘特图。
- **🔗 串联**：共享同一批文件或同一张表，必须一个人连续做完，禁拆多写手。
- **🔀 并行**：彼此不碰同一文件，可以多人或多代理同时开。
- **🚪 汇合**：等上游全部收口才能开，通常是一个集成票或 QA 票。

排期问答用一句话回答：**「立即可并行的票池」+「必须顺序推进的串联链」**。

### 4.3 票切到多细

三条判据，全过才算一张票：

1. 一次上下文装得下（单票改动 ≤6 个文件）
2. 做完能当着人点一遍
3. 硬依赖真实（不是「相关」）

**真并行矩阵**：以下情况必须串，其余可并。

| 情况 | 判定 | 原因 |
| --- | --- | --- |
| 改同一张表 / 同一次迁移 | 🔗 串 | 迁移序号必须连续，并发会撞 `_journal.json` |
| 改共享契约（`packages/shared`） | 🔗 串，先合再改 | 字段漂移会连锁 |
| 改共享注册标记（路由表、菜单、权限码） | 🔗 串 | 合并冲突修不干净 |
| 纯页面切片、纯配置、纯文案 | 🔀 并 | 不碰共享文件 |
| 独立端（H5、小程序壳） | 🔀 并 | 不进主注册表 |

### 4.4 派发协议（Router 五步）

1. 读依赖票的**交付回执**与对应 Spec 小节，不重造
2. 判断票类型：`Base` 扩底座、`Module` 走五要素生成、`QA` 只验收
3. 按串并规则决定「现在能开哪几张」
4. 给每张票指定执行者：`fde-逐单`（实现）、`fde-verify`（验收）、人（拍板）
5. 票上写清授权范围与「不碰」清单

票的类型决定执行者，不靠猜：

| 票类型 | 执行者 | 产出的证据 |
| --- | --- | --- |
| `Base` / `Module` 实现票 | `fde-逐单` | `E5-*.json` |
| `QA` 验收票 | `fde-verify` + 人 | `E6-*.json` |
| 拍板 / 授权 | 人 | 决策卡 |

### 4.5 三阶段勾选与越权边界

每张票三个复选框，**AI 只能勾第一个**：

- ① `AI 首轮实现`：自检与门禁绿后由 AI 勾，并填交付回执
- ② `人工走查`：人对照原型与擦屁股清单走查后勾
- ③ `QA 封票`：验收通过后由人或 QA 勾

这条抄自实例，理由是防「AI 自己宣布完成」。代勾第二、三项等于伪造验收——比不勾更坏。

### 4.6 四拍节奏

```text
① AI 冲刺出骨架（跑绿门禁，勾 ①，写回执）
② 人 2 分钟走查（对照原型与擦屁股清单，集中记缺陷）
③ AI 集中擦屁股（按缺陷清单一次性修，回归后由人勾 ②）
④ QA 滚动验收（跑 AC 用例，勾 ③ 封票）
```

四拍的价值在于：**人只在第 2 拍集中出现一次**，不用全程盯着。这与 v0.3 的「人只审五页、只点验收卡」是同一个设计。

### 4.7 防撞八条（多端版）

前四条第来自实例，后四条是 fde 自己的：

1. 多工作树并行改库，按「先合 A → rebase → 再生成迁移」顺序
2. 不预先把业务表写死进 `schema.ts`，交给生成器追加区块
3. 不删生成器的区块标记与 `#region` 配对注释
4. 多代理禁用同目录并发（会撞 `dist` 缓存与 sqlite 文件）
5. 单文件 400 行主动拆，450 行是硬上限
6. 规格文件平铺 `docs/specs/`，不按波次建子目录
7. 路由挂载不带 `/api` 前缀（代理层已统一）
8. 非 React 端（H5 / 小程序壳）不进 Web 端注册表

## 5 测试生成与自测

### 5.1 三层测试，来源各不相同

| 层 | 测什么 | 用例从哪来 | 谁写 | 判据 |
| --- | --- | --- | --- | --- |
| 单元 | 业务不变量、边界值 | S6 状态机 + S7 业务规则列 | Worker 红绿 | 每条不变量至少一条负例 |
| 接口 | 鉴权、分页、审计、幂等 | S3/S4 权限 + S11 的 Given | Worker | 401/403/409 各一条 |
| E2E | 用户能不能走通 | S11 的 AC + S5 主链 | Worker 写、QA 跑 | 阻塞场景四类全覆盖 |

**测试不许现编**：用例的编号必须能追到 `AC-` 或 `BR-`，追不到的就是自己发明的测试。

### 5.2 E2E 覆盖矩阵（四步法）

1. **逐章提取可测断言**：从 PRD 每节抽「可以判真假」的句子，一句一条断言草稿
2. **按业务能力分组**：不按功能模块分，按「用户要完成的事」分（申报、评审、发证、缴费）
3. **生成覆盖矩阵**：行是业务能力，列是主路径 / 异常 / 权限 / 数据边界，标出空档
4. **反向校验**：拿矩阵回对 S11，缺的补、多的删

矩阵落成一张表，随 `E5` 证据一起交。空档要么补用例，要么在「未覆盖说明」里写清为什么。

### 5.3 阻塞场景必测四类

抄实例的清单，这是「测试全绿但人一用就卡」的解药：

1. **登录**：正常登录、密码错、账号禁用、会话过期跳转
2. **菜单导航**：每个一级菜单点得开、不 404、权限不够时不显示
3. **CRUD 闭环**：建 → 列表可见 → 编辑 → 详情正确 → 删除后不可见
4. **数据权限**：A 角色看不到 B 角色的数据、越权接口返回 403

这四类不过，其余用例全绿也不算过 E6。

### 5.4 无头还是有头：分工，不是二选一

结论先说：**无头跑门禁，有头跑诊断与视觉基线；两边跑同一批用例，结果对不上就判失败。**

为什么不能只留一种：

| | 无头 | 有头 |
| --- | --- | --- |
| 速度 | 快，可并行分片 | 慢，窗口创建与渲染开销大 |
| CI | 原生支持 | 要虚拟显示，成本高 |
| 稳定性 | 高，无窗口管理器干扰 | 低，焦点抢占、缩放、系统弹窗 |
| 保真度 | 同一渲染引擎，但 GPU 合成、字体光栅、原生文件选择器仍有差异 | 与用户所见一致 |
| 能测什么 | 页面内行为 | 窗口级行为：文件选择、下载、剪贴板、打印、多窗口、HTML5 拖拽 |

这套项目的设计系统大量用毛玻璃（`backdrop-filter`），它走合成层，无头与有头的像素结果可能不同——**视觉基线不能两边混用**，这一条是硬规则。

**分工表**

| 用途 | 模式 | 频率 | 判据 |
| --- | --- | --- | --- |
| 阻塞场景四类 + 主链 | 无头 | 每票、每次交付 | 全绿，且与有头结果一致 |
| 视觉基线截图 | 有头 | 页面定型时拍一次，之后只在 UI 改动时重拍 | 同浏览器版本、同视口、容差 5% |
| 失败复现 | 有头 | 按需 | 能复现是产品 bug；不能复现记环境差异 |
| 原生能力（上传、下载、剪贴板、打印、多窗口、拖拽） | 有头 | 涉及才跑 | 用例标 `headed-only` |

**工具选型：一套 Playwright，不引第二套。**

理由不是偏好，是「一份用例两个模式」这条规则本身：只有同一个 runner 才能让同一份 spec 在两种模式下跑，结果才可比。换工具就得写两套用例，parity 立刻失效。

有头模式用 `channel: 'chrome'` 走**真 Chrome**，不用 Playwright 自带的 Chromium——用户用的是 Chrome，毛玻璃、字体光栅、原生控件的表现要贴着它。代价是版本会漂，所以：

- 版本锁 **Chrome for Testing**，不用系统自动更新的那个；
- 证据里记 `browser.version`，与基线不一致即作废；
- 基线按平台分目录（Windows 与 macOS 字体不同，不能共用）。

配置形状（示意，四类 project 各管一段）：

```ts
projects: [
  { name: 'headless', use: { ...devices['Desktop Chrome'], headless: true } },
  { name: 'headed',   use: { ...devices['Desktop Chrome'], channel: 'chrome', headless: false } },
  { name: 'visual',   testMatch: /.*visual\.spec\.ts/, use: { channel: 'chrome', headless: false } },
  { name: 'headed-only', testMatch: /.*headed-only\.spec\.ts/, use: { channel: 'chrome', headless: false } },
]
```

**Google 的工具留在调试位，不进门槛**：

| 工具 | 用来干什么 | 为什么不当执行器 |
| --- | --- | --- |
| Puppeteer | 临时抓一次 DOM/网络，写一次性脚本 | 没有测试 runner，断言、重试、trace、登录态复用都要自己搭；再搭一遍等于重造 Playwright |
| Chrome DevTools MCP | 让 agent 读控制台、网络、性能面板排障 | 它是交互式调试通道，不是批量执行器，跑套件不合适 |
| Lighthouse | 性能与可达性指标 | 与功能验收不是一回事，单独成一份报告 |

一句话：**跑套件用 Playwright，查明问题可以用 Chrome DevTools MCP，两者不混。**

**怎么确保它真的这么跑**（不靠自觉）：

1. **一份用例，两个 project**：同一份 spec 文件，Playwright 配 `headless` 与 `headed` 两个 project，不写两套代码。
2. **证据记模式**：`E6` 证据里必须有 `e2e.mode`、`browser.version`、`viewport`、`reducedMotion`，缺一项判证据无效。
3. **一致性门（parity）**：交付前同一批核心用例两模式都跑，结果 diff 必须为空；不一致就不许交付，先查是环境差异还是产品 bug。
4. **只能有头的用例要登记**：票上写 `headed-only: 原因`，进 E6 清单；没标注又不跑，算缺证据。
5. **禁止拿手动截图冒充 E2E**：有头截图是人卡的证据，自动化证据必须来自脚本。两者在证据 schema 里分属 `card` 与 `script`，不能互换。

**稳定三板斧**（两种模式都要）：关动画（`reducedMotion` 加禁用 CSS 动画）、固定视口与 DPI、固定浏览器版本。三者任一漂移，截图基线作废。

### 5.5 E2E 基建六条（两种模式共用）

1. **双 project**：无头跑 CI，有头跑本地排障与视觉基线，同一批用例
2. **seed 单源**：账号与造数由同一个脚本生成，mock 与真实库共用定义
3. **登录复用**：`storageState` 保存登录态，不每个用例重登
4. **选择器**：`data-testid` 优先，禁按样式类或文案定位
5. **禁 `waitForTimeout`**：等元素状态，不等时间
6. **失败留证**：截图 + trace + 控制台日志，落进 `evidence/`

视觉回归只对稳定页面做，容差 5%，意外 mismatch 修代码不改基线。

### 5.6 自测量化（E5 的判据）

- 每个 `AC-` 至少一条自动化断言（接口或 E2E）
- 每条业务不变量至少一条负例
- 覆盖矩阵里「主路径」列不许有空档
- 测试静态检查四件：文件非空、接口真实存在、fixture 类型一致、负例数够
- 反恒真：期望值来源可指认（规格原文 / 手工算例 / 字面量）
- **数据断言条数不为零**：每张票至少一条数值/状态/关联断言，纯 UI 断言的票不算验过（见 5.8）

### 5.7 自测报告

Worker 交票时附一段，格式固定：

```text
票：W1-T03
验收：AC-C01 ✅ / AC-C02 ✅
覆盖矩阵：4 项主路径全绿；异常 2/3（并发审批未复现，见未覆盖说明）
负例：4 条（状态非法 2、权限 1、金额越界 1）
数据断言：3 条（金额 2、状态 1）；明细合计 = 汇总 12345.00 元 ✅
门禁：check 退出 0
未覆盖说明：并发审批需两人同时操作，留人工走查
证据：evidence/E5-03.json
```

### 5.8 数据断言：跑通不算过

页面点得通、接口 200，只证明它没坏，不证明**算得对**。财务与业务数据必须单独验，而且验在数据层，不验在界面上。

**六类数据断言，每票按需选**：

| 类 | 验什么 | 例 |
| --- | --- | --- |
| 金额与精度 | 单位、舍入、边界（0 / 负 / 超限） | 报价 999.995 按规则入到 1000.00；0 元单允许生成；负数被拒 |
| 状态与快照 | 流转后字段值、历史快照不可变 | 归档后 `status=archived` 且 `archived_at` 非空；旧快照不随主表改 |
| 编号与唯一性 | 生成规则、并发不重号 | 合同号 `HT-2026-0001` 连续；并发创建 50 单无重复 |
| 关联一致性 | 主外键、汇总 = 明细合计 | 一张缴费单 3 条明细，合计必须等于单头金额 |
| 幂等与重放 | 重复提交不产生双份 | 同一请求发两次，订单数仍为 1 |
| 审计留痕 | 前后值、操作人、时间 | 改金额后审计 diff 里 `before=100.00 / after=200.00` |

**三条硬规矩**：

1. **期望值必须来自独立算例**。手工算一遍写进 S11，不许用实现同样方式重算——那等于自己证明自己。
2. **金额按最小单位（分）比较**，禁止浮点直接比较；涉及税率、折扣、分摊时，先定舍入规则再写断言。
3. **守恒断言优先**。汇总 = 明细和、期初 + 收入 − 支出 = 期末，这类等式比逐字段比对更能抓出真错。

**验在哪一层**：

```text
界面断言：看得见（必要，不充分）
接口断言：返回体字段值对不对
数据库断言：落库值对不对（同一次事务里查）
不变量断言：跨表/跨期是否守恒
```

只写第一层的票，E5 判不过。

**人的那一步**：E6 验收卡里固定留一项「抽 1–2 笔手工验算」——AI 报 `12,345.00`，人拿计算器按一遍。这条不是不信任自动化，是防「测试和实现犯同一个错」。

## 7 技能自验收

**触发评测**：≥8 条正例 + ≥8 条负例（含与相邻能力的边界），description 跑通全部用例才动工；改一次 description 重跑一次。

**交付评测**：固定 3 条真实小需求（P0 前定死），同一模型分别带技能 / 不带技能各跑一遍，比完成率、人工介入次数、token。

**验收指标**：非工程人员独立完成率 ≥50%；门禁一次通过率 ≥60%；技能增益 ≥30 个百分点；入口常驻 ≤200 行。

## 10 三条最容易写歪的地方

1. **把 reference 写成教程**。判据必须可判定，不写「要仔细检查」这类话；写不出判据的段落，删。
2. **票的粒度按功能模块切**。应按「用户能演示的一条竖切」切，否则每张票都验收不了。
3. **E2E 写成快乐路径合集**。必须覆盖阻塞四类与异常分支，否则测试全绿仍然是假绿。
