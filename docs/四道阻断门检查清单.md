# 四道阻断门检查清单 v0.1

> 配套《all-in-fde 方案 v0.3》§5.2。四道阻断门是 **E0 环境、E5 实现、E6 人用、E7 交付**；E1–E4 是检查项，只记录、不阻断。
>
> 用法：每个项目按顺序跑一遍，每项落一条证据到 `.fde/evidence/`。三态：PASS / FAIL / SKIP。**SKIP 必须写原因，不冒充绿。**
>
> 本文件是清单，不是脚本。具体命令由实现期定，`bun run check` 这类是约定名。

---

## 0 通用规则

**谁写证据。** 脚本类由脚本自己写（命令、退出码、时间戳）；人卡类由卡片工具写。agent 只读，不许代写——这条是 P1 的硬补充，别放松。

**一条门一个文件。** `E0-<日期>.json`、`E5-07.json`（按票）、`E6-01.json`（按卡）、`E7-<日期>.json`。

**最小字段。** 字段名、31 条检查项的 ID、门级聚合规则与 JSON Schema 见[证据 schema 与门禁 ID 对照](./证据schema与门禁ID对照.md)。下面只是抄录，以那份为准。

```text
gate      门编号与项号，如 E5-4
at        时间戳（ISO 8601，带时区）
cmd       实际跑的命令；人卡写"卡片 id"
exit      原始退出码；人卡写选择结果
artifact  产物路径（日志、截图、测试报告）
summary   ≤5 行，写"看到了什么"，不写"感觉没问题"
by        执行者标识（脚本名 / 人 + 首字母）
mode      PASS / FAIL / SKIP
```

**三态怎么算。**

- PASS：命令退出 0 且 summary 能对上判据
- FAIL：退出非 0，或输出与判据不符
- SKIP：环境不具备、没真正检查。**必须写原因和补救办法**，且该门整体不能算通关

**失败怎么办。** FAIL 只有两条路：修好重跑，或降级为「已知问题」并写进交付说明。不许把 FAIL 改写成 SKIP，也不许口头说「这个不影响」。

**独立复核。** E5 至少抽查一张票，由另一个会话只读复核，不看实现者的推理过程。

## 1 E0 环境（阻断｜脚本｜新机器必跑）

前置：新机器、换目录、或距上次成功超过 30 天。

- [ ] **E0-1 运行时**：`bun --version` 与 `node --version` 都在支持区间内
- [ ] **E0-2 版本控制**：`git --version` 可用；当前目录已是仓库，或能干净 `git init`
- [ ] **E0-3 依赖可装**：在临时副本跑一次安装，不污染工作区；失败要能读出是网络还是权限
- [ ] **E0-4 端口可用**：约定的前后端端口没有被旧进程占着
- [ ] **E0-5 模板可达**：模板仓库能连通（`git ls-remote` 或等价探测），5 秒内返回
- [ ] **E0-6 磁盘与写权限**：工作目录可写；剩余空间够装依赖与数据库（经验值 ≥2GB）

**通过的样子**：六项全 PASS。离线环境允许 E0-5 记 SKIP，但必须写清「离线模板已预置在哪」。

**假绿常见**：只跑 `bun --version` 就算过；端口检测跳过后直接起服务，撞端口再回头查。

## 2 E5 实现（阻断｜脚本 + 复核｜每张票一次）

前置：票已切好，规格书对应小节存在。

**验收与门禁**

- [ ] **E5-1 验收谓词逐条有证据**：票上 3–5 条，每条对应一个测试名、一次点击或一条命令输出。缺一条即 FAIL
- [ ] **E5-2 门禁全绿**：`bun run check`（类型、静态检查、架构检查、测试、迁移一致性）退出 0
- [ ] **E5-3 测试静态检查**：测试文件非空；测试引用的接口在契约里真实存在；fixture 字段类型与 schema 一致

**防假绿三条**

- [ ] **E5-4 seam 预确认**：每条测试都写在规格书确认过的公开边界上；测试文件头写清「抓什么、漏什么」
- [ ] **E5-5 反恒真断言**：期望值来自独立真相源（规格书原文、手工算例、已知字面量），不是用实现同样的方式重算一遍
- [ ] **E5-6 测行为不测实现**：只经公开接口观察；mock 只打外部边界

**不变量与范围**

- [ ] **E5-7 不变量负例**：规格书里每条业务不变量，至少有一条「应该被拒绝」的测试
- [ ] **E5-8 范围核对**：diff 只在授权范围内；命中越界判据（改授权外文件、改公共接口或加依赖、超行数阈值）即 FAIL

**复核**

- [ ] **E5-9 独立复核**：抽查至少一张票，由另一个会话只读复核；复核不通过即 FAIL

**通过的样子**：E5-1 到 E5-9 全 PASS。

**假绿常见**：测试只覆盖快乐路径；断言恒真（`expect(true)`、拿实现输出当期望值）；把真实校验 mock 掉；E2E 只跑 Mock 就当验过。这四种脚本查不出来，只能靠 E5-4 到 E5-6 的人看。

## 3 E6 人用（阻断｜人卡 + 冷启动｜交付前一次）

前置：E5 全过。**这一门不看测试结果，只看人能不能用。**

- [ ] **E6-1 删库**：删掉数据库文件或重置，模拟全新部署
- [ ] **E6-2 后端冷启动**：启动日志里种子账号数量等于预期数量
- [ ] **E6-3 前端启动**：端口与配置一致，没有漂移
- [ ] **E6-4 逐角色登录**：登录页上真实存在的账号逐个登录成功，各自落到正确页面
- [ ] **E6-5 禁用与改密**：被禁用账号登录被拒；需改密账号弹出改密页
- [ ] **E6-6 核心旅程**：走一条主路径（如新建→审批→通知），每一步有可见结果
- [ ] **E6-7 异常分支**：403、409、空态、超长输入各点一次，表现与规格一致
- [ ] **E6-8 控制台**：浏览器控制台无 A 类报错；有非 A 类报错要逐条登记
- [ ] **E6-9 验收卡**：3–5 项，每项指到可打开的东西（文件行号、页面路由、截图、测试名），人点选后无「有问题」；其中固定一项是「抽 1–2 笔数据手工验算」
- [ ] **E6-10 E2E 真实模式**：核心链路在真实后端上跑通，不是 Mock

**通过的样子**：十项全过，且卡上没有「有问题」。

**假绿常见**：没删库，用开发库里的老数据蒙混；E2E 跑 Mock 冒充真实链路；验收卡写成「页面正常」这种不可判定的话。**冷启动这条最值钱，别省。**

## 4 E7 交付（阻断｜脚本 + 干净目录复跑｜交付时一次）

- [ ] **E7-1 干净目录**：复制到新目录或新容器，不带依赖目录、不带数据库
- [ ] **E7-2 按 README 装与起**：只照 README 操作，不靠记忆补步骤；起不来即 FAIL
- [ ] **E7-3 冒烟**：首页能开、能登录、主路径能走
- [ ] **E7-4 回滚**：按回滚说明退回上一版，能正常启动
- [ ] **E7-5 内网坐标扫描**：交付物里没有内网地址、账号、令牌路径（扫描器三态退出码，不是二态）
- [ ] **E7-6 已知问题登记**：所有 SKIP 与已知问题在交付说明里列全，含复现方式

**通过的样子**：六项全过。

**假绿常见**：在自己机器上复跑（环境已经被改过，不算干净）；README 缺步骤但「我记得」；回滚只在脑子里演过一遍。

## 6 什么时候可以宣布可交付

四个条件同时成立：

1. E0 全 PASS（或 SKIP 有正当理由与替代）
2. 所有票的 E5 全 PASS
3. E6 全过，验收卡无「有问题」
4. E7 全过，且没有未登记的 FAIL

少一条就不是交付，是「做完了但没验」。

## 7 清单自身的维护

这份清单也会腐化，规则和技能一样。

- **每出现一次假绿，加一条判据**，加在对应门的 items 里，不许只写进复盘文档。这是 all-in-mvp 血案库的正确用法：现象变判据，不是变感想。
- **每条必须有执行体**：脚本或卡片。没有执行体的条目移出阻断清单，放进「人工注意」，不占阻断位。
- **季度修剪**：连续三次没拦住任何问题的条目删掉。清单越长，越会被整段跳过——这正是 all-in-mvp 四十条规则里六成没人看的教训。
