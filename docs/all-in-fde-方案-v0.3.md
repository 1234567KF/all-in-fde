## 0 一页纸

**一句话**：all-in-fde 是一个入口技能。它把「会用电脑的人 + 一个空目录 + 一句话需求」推到「可验收的小型 IT 系统」——它让每一个动作都留下能复跑的验收证据，不靠 AI 记住流程。

**交付物**

1. 一个入口技能（description 常驻约百 token，正文不超过一页、按需加载）
2. 七个动作的编排规则，每个动作一条出口判据
3. 一套证据门禁（E0–E7）与 `.fde/` 目录约定
4. 接上现成脚手架，不自建
5. 面向非工程人员的引导话术（每步只问 1–3 个选择题）
6. 一个可选执行引擎（Super-agent），票多、要并行时启用（§15）
7. 一套需求采集表模板（十六张表 → PRD 分卷 → 原型），A1 的工件（§6.7）

**五个判断**

| 来源 | 学什么 | 不学什么 |
| --- | --- | --- |
| gspowers | 流程地图、随时可恢复、上下文清理边界、可选步骤显式跳过、经验回流 | 用 `state.json` 记阶段；用固定 11 步套所有项目；导航员只报站不执行 |
| mattpocock | 完成判据先于步骤；依赖边替代阶段；只做待办前沿；窄竖切、宽重构例外；触发词决定技能何时被想起 | ——（其「不需要状态机」的结论本方案接受，但落到「证据派生状态」这一具体做法） |
| all-in-mvp（本机实测） | 票上写状态、契约唯一真源、冷启动冒烟、防假绿三条、血案库 | 阶段门加散文门禁；靠不断加规则修补；技能长到 3,012 行 |
| Super-agent | Router/Worker 分工、授权范围、两级准入、注意力闸门、看门狗三判据 | 把票状态搬进 SQLite；Worker 全权限当默认；自动合并 |
| 参考脚手架 | 人机边界（4 做 4 不做）、5 要素规格书、6 道门禁、2 分钟人审 | 不重造工程流水线；不让非工程人员碰 git、端口、迁移细节 |

**不做什么**

- 不做通用项目管理系统，不做低代码平台，不做模型微调
- 不承诺零人工。人的时间预算：设计决策 + 抽查，单模块不超过 30 分钟
- v0.2 不覆盖：遗留系统改造、多实例与高并发、涉密合规审计

## 1 四份材料各自解决了什么

### 1.1 gspowers：把「下一步做什么」产品化了，把「做到没有」交给了人的自述

机制（原文）：

- 一个 skill 当导航员，读 `.gspowers/state.json`，画流程地图，提示下一步该敲什么命令。它明确写着「你不自动执行子 skill——只提示用户该执行什么命令」。
- 恢复模式先问用户「上一步（`current_step`）完成了吗？」，回答是才推进。
- 11 步固定序列：office-hours → plan-ceo-review → plan-eng-review → brainstorming → writing-plans → subagent-dev → review → qa → ship → compound → document-release；靠 `/clear` 在 gstack 与 superpowers 两条工具链之间切换。
- v1.1 加了知识回流：ship 之后 `/ce:compound` 把经验写进 `docs/solutions/`，下一轮 brainstorming 前自动检索。

**值得抄四处**：流程地图（人一眼知道自己在哪）、`handoff.md` 摘要（换会话还能读）、`/clear` 边界（换工具链时清上下文）、可选步骤显式标 `⏭️` 跳过而不是假装做过。

**不能抄两处**：

1. **状态靠自述**。「完成了吗」由人回答，而人在赶进度时最容易答「完成了」。于是状态机记的是意图，不是事实。
2. **序列硬编码**。11 步对「加一个字段」是灾难；跳过靠人临场判断，跳过记录又不影响后续判据。

结论：保留它「看得见」的部分，换掉它「说了算」的部分。

### 1.2 mattpocock：稳定性来自判据、依赖边和反馈回路，不来自阶段字段

这套技能针对四个失败模式：没做对（`/grill-with-docs` 追问到每个分支都有答案，同时长出术语表与 ADR）、太啰嗦（共享语言）、代码不跑（类型 + 浏览器 + 测试，`/tdd` 红-绿-重构）、建成泥球（深模块设计）。与本题最相关的三条机制：

1. **完成判据**。每个步骤必须以「能判断做完没有」的条件收尾，判据要「可检查 + 穷尽」。判据一含糊，就会诱发 *premature completion*——注意力滑向「看起来做完了」，而不是「真的做完了」。
2. **依赖边**。`/to-tickets` 把计划切成 tracer bullet 竖切，每张票声明「被谁阻塞」，只做没有阻塞的 frontier（原文叫 ticket，白皮书叫「任务工单」，本文统一叫「票」）。宽重构（改一个符号炸一片调用点）是例外，走 expand–contract：先并存、再分批迁移、最后删除。
3. **触发可靠性**。技能分两类：user-invoked（零常驻上下文，只花人的记性）与 model-invoked（常驻一段描述，换自动触发）。技能一多就用 router 收敛成一个入口。指针怎么写，比文档放哪里更决定它会不会被想起来。

它没有状态机，但有四样东西：入口路由、每步判据、依赖图、硬反馈回路。这四样给出的确定性比一个 `current_step` 字段更强——因为判据和测试会真的失败。

### 1.3 参考脚手架：人机边界已经写成了可执行文件

- 人只做 4 件事：丢原始需求 → 答几个边界选择题 → 审一页 Markdown 表格点确认 → 看一眼页面与核心业务规则。
- 人不用做 4 件事：不用建目录、不用填模板、不用敲 `gen:module`、不用维护规格书版本号。
- 5 要素规格书（实体字段 / 业务不变量 / 权限 / 审计 / 界面布局）+ 6 步流程 + 6 类门禁（typecheck、lint、migrate:check、arch:check、test、单文件 450 行棘轮）+ 2 分钟人审三处。
- 技术底：Bun、Hono、Drizzle + bun:sqlite、React 19 + Tailwind v4 + shadcn 白盒组件、Zod 共享契约、AST 门禁。

结论：工程段的防呆已经做完了。all-in-fde 的价值只能在前段（把一句话变成 5 要素和票）和后段（把「跑绿了」变成「人能用」）。中间那段不要碰，接过去就行。

### 1.4 合起来的主线

三份材料指向同一件事：**AI 的不确定性不在「顺序」，而在「是否真的做完了」和「做完的是不是要的」。** 状态机约束的是顺序，顺序在七个小动作里本来就不稀缺，人能记住；稀缺的是「做完了吗」的可验证性。所以预算应该从「记状态」挪到「产证据」，从「排步骤」挪到「写判据」。这就是下面 P1、P2 两条原则的由来。

### 1.5 all-in-mvp 的实测：门禁为什么会失败

本机 `D:\all-in-mvp` 是一套跑了 28 个版本的同向框架，它的复盘材料比任何理论都直接。

| 资产 | 规模（他们的实测） |
| --- | --- |
| 技能 | 26 个 SKILL.md，合计 17,146 行 |
| 主技能 | `all-in-mvp` 一份 3,012 行 |
| 调度器 | `kf-pipeline-coordinator` 1,332 行 |
| 门禁规则 | `gate-rules.yaml` 637 行 / 40 条，其中 24 条没有检查脚本 |
| 血案库 | `PLAYBOOK.md` 32 条，每条对应一条或几条规则 |
| 单任务预算 | 自己定的 4,000 token |

根因不是哪条规则写错，是增长模式：出一个血案 → 加一条规则 → 配一道门 → 门产生新例外 → 再加补丁。v2.5 到 v2.28 的版本号就是补丁层数。

三个结构性失败，每一个都直接命中我们的设计：

1. **门禁只守前门**。质量门自己写着「修复模式不走 Stage 流程 → 全部检查失效」，于是又给修复模式单开一道小门。旁路一旦存在，就永远补不完。

2. **六成门禁是散文**。40 条规则里 24 条没有检查脚本——写给模型看的 MUST，拦不住模型。

3. **控制层自己成了故障面**。frontmatter 解析失败，技能在列表里静默消失但 agent 还能调到；钩子要重启会话才生效；同一批规则在三个文件里各写一遍，改一处忘两处。

**它做对了、必须保留的五样**：Zod 契约唯一真相源、真实浏览器冒烟（冷启动、菜单完整性、核心旅程、console 错误、A 类阻塞）、Playwright 有头与无头结果一致、starters 脚手架、内网坐标扫描。这五样是「无人值守」的定价，不是仪式。

**它踩过、我们必须绕开的两件事**：

- E2E 跑在 Mock 服务器上，人工验收跑真实后端，种子数据两份不同步——92 条用例全绿，人一登录就报密码错误。测试环境与验收环境不是同一套后端，是全绿但一挂就挂的根源。
- 端口「用户要求 2222/3333」只存在口头约定，没写进任何文件，最后三个配置文件各自硬编码了 3000 和 5173。

他们自己算过一笔账，值得抄：**Matt 体系预设强模型加人在环，无人值守并行要额外付派发器、票出口、交付硬门三样成本。减的是仪式，不是保险。** 我们的七个动作按这条称重。

这些教训在方案里的落点：§4 轻量档、§5.2 门禁分层、§5.5 冷启动、§8.7–8.9；反过来，它做对的那部分有哪些能直接搬，盘点在 §14。

## 2 九条设计原则

**P1 证据即状态（derived, not maintained）**
进度不写字段，由 `.fde/evidence/` 里能复跑的门禁结果推导。状态只有两个载体：票（写了执行者与意图状态）和证据（写了命令与退出码）；两者都在文件系统里，崩溃恢复就是读目录重开未完成的票。要维护的状态一定会在压力下撒谎；证据是产物，撒谎得伪造文件，成本高得多。副作用是「恢复」变成扫描目录，不需要再问人一句「上次做到哪了」。

**P1 的硬补充：证据写入权。** 上面「伪造成本高」只对成立于人，对 agent 不成立——agent 手写一个证据 JSON 是零成本动作。所以证据文件只能由门禁脚本或卡片工具写出：脚本跑完自己写出命令、退出码、时间戳，agent 只读不写；人卡结果由卡片工具写出。让 agent 代写证据，等于把 gspowers 的自述状态换了个文件格式请回来。DSH 支持写入钩子时再加一道拦截（见 §5.6）。

**P2 判据先于步骤**
先写「怎么算完」，再排「先做什么」。每条判据必须能被一条命令或一张清单判定；判不了，说明这个动作切错了，而不是判据写得不够努力。

**P3 入口唯一，技能按需**
常驻上下文只留一个入口技能；其余能力做成入口技能里的 reference 分支，按触发词加载。一次只加载当前动作的那一个分支，不预加载下一个动作。理由是成本结构：常驻的每个字每一轮都要付，而人的记性只有一份。技能数量按「升格三条」控制，见 §7。

**P4 顺纹切，依赖显式**
沿现有接口竖切（不动契约、不跨模块）是顺纹，能并行；改共享契约是逆纹，先 expand 再 migrate 再 contract。每张票只声明真实阻塞边，宁可串行，不要假并行。

**P5 省在刀背，花在刀刃**
算力、token、时间、注意力都是预算。强模型用在判定（切片、验收、审查），便宜模型用在产出（草稿、批量改、长文）；重活放低价时段；上下文里只留当前这张票需要的东西。

**P6 门禁必须有执行体**
一条门禁要么绑一条命令（有退出码），要么绑一张人卡（有签名）。两样都没有的，不叫门禁，叫建议。别人的实测是：40 条规则里 24 条是散文，六成门禁等于没有。这条也决定门禁的数量——能脚本化的写成脚本，写不了脚本的降为检查项，不进阻断门。散文越厚，绕路的理由越多。

**P7 票是凭据，不是档案**
票回答「派给谁」和「拿什么算完」，不回答「界面长什么样」。字段、按钮、弹窗、交互的唯一定义在规格书；票只引用编号，最多带 3–5 条可判定的验收谓词。票一旦变成需求文档，就有了第二份真相，改一处必忘另一处。

**P8 授权先于执行**
每张票出门前先写清三件事：谁授权的、允许改动哪些目录、什么情况必须停下来问。Super-agent 把这份东西叫授权范围（Mandate），做成不可变对象，越界即停。没有授权范围的票，等于给执行者一张空白支票；无人值守时，这张支票会自己兑现。

**P9 打扰是稀缺资源**
只有三种情况允许打断人：结果可用了、需要人拍板、做不下去了。其余一律静默，进度只写进记录。打扰必须是一个具体问题加选项，不是一段汇报。这条把人「只在两处出现」从口号变成准入条件：不满足这三种许可，消息发不出去。

## 3 架构

```text
┌──────────────────────────────────────────────────────────────┐
│ L0 入口  all-in-fde（description 常驻，正文 ≤1 页按需加载）      │
│   扫 .fde/ → 推导进度 → 只讲下一步要什么、判据是什么             │
└───────────────┬──────────────────────────────────────────────┘
                │ 按触发词加载，不常驻
┌───────────────▼──────────────────────────────────────────────┐
│ L1 编排  七个动作的 reference 分支                              │
│   收活 / 校准 / 切片 / 起架 / 逐单 / 验收 / 交付                 │
└───────────────┬──────────────────────────────────────────────┘
                │ 同一套票，可交给两种执行者
┌───────────────▼──────────────────────────────────────────────┐
│ L1.5 执行引擎（可选）  Super-agent                              │
│   Trigger → 准入（规则快筛 → 模型慢筛）→ 票 + 授权范围          │
│   → Worker（一单一会话一工作树）→ 报告 → 交付（patch / PR）      │
│   贯穿：注意力闸门（三种许可）+ 看门狗（无进展 / 死循环 / 跑偏）   │
└───────────────┬──────────────────────────────────────────────┘
                │ 调现成能力，不重写
┌───────────────▼──────────────────────────────────────────────┐
│ L2 领域  现成脚手架（6 类门禁 + 2 分钟人审 + 450 行棘轮）           │
│         business-feature-builder（5 要素 → 全栈落码）            │
│         tdd / e2e / 导出（docx、xlsx）                          │
└───────────────┬──────────────────────────────────────────────┘
                │ 产出即证据
┌───────────────▼──────────────────────────────────────────────┐
│ L3 证据  .fde/{brief,spec,tickets,evidence,handoff,retro}       │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 常驻成本 | 谁维护 | 失效表现 |
| --- | --- | --- | --- |
| L0 入口 | description 约百 token；正文 ≤1 页按需 | 技能作者 | 触发词或地图不准，人迷路 |
| L1 分支 | 0（按需） | 技能作者 | 某个动作的判据漂移 |
| L1.5 引擎 | 0（不装就没有这一层） | 引擎维护者 | 派发失控、跑偏无人拦 |
| L2 领域 | 0（按需） | 脚手架维护者 | 门禁升级，需跟版本 |
| L3 证据 | 0 | 运行时自动写 | 进度不可推导，退化成问人 |

L1.5 是可选层：只有一张票的项目，同屏做完最省；票多到要并行、或者人不在场时，才接引擎。两层用的是同一套票与证据，换层不改票。

### 3.1 项目结构：四端一套骨架

多端项目（管理端、企业门户、作业小程序、公众号 H5、扫码落地页）不复制仓库，用一个 monorepo 加分端注册表：

```text
web-apps.json                 # 端注册表：id / base / devPort / title / accessPermission
apps/
├── web/                      # 默认端：路由、菜单、页面、services、hooks/queries
├── portal/                   # 企业门户（同上结构，独立 base 与 devPort）
└── api/                      # Hono + Drizzle + bun:sqlite
packages/
├── shared/                   # Zod 契约、枚举、权限码注册表（唯一真相）
├── ui/                       # 设计系统（只靠 props，不 import web-core）
└── web-core/                 # 前端内核（api 客户端、query、toast、权限消费）
eslint-rules/                 # AST 单文件规则
scripts/                      # arch:check、gen:module、add:web 等
```

四条结构约束（都有机器执行体，不靠自觉）：

1. **新增端只改注册表**。`web-apps.json` 加一行，其余由 `add:web` 生成；手抄第二个 `apps/web` 一律不合格。
2. **依赖方向单向**：`apps/* → web-core → shared`、`apps/* → ui`；`ui` 不得 import `web-core`，端与端之间禁止互相 import。
3. **每个端自带四件套**：路由（`App.tsx` 懒加载）、菜单（`menu-config.ts`）、query key 工厂、权限消费（只读后端下发的 `permissions`，不自己推角色）。
4. **共享包只在第二次被用到时才提升**。一个端用的东西留在端内，两个端都用才提进 `packages/`，避免提前抽象。

**产物脱敏**：技能产物不写内网地址、内部仓库路径、内部项目名与内部工具名，判据与命令见 §11.7。方案本文不受此限。

### 3.2 架构门禁：能脚本化的才算门禁

单文件规则交给 ESLint AST，跨文件不变量交给扫描脚本，两者都在 pre-commit 与 CI 双重拦截：

| 规则 | 守护什么 | 失败表现 |
| --- | --- | --- |
| `no-tailwind-raw-colors` | 禁止 `text-red-500` 与内联 hex/rgb，强制语义 token | 颜色改一处必须改十处 |
| `no-service-import-in-ui` | 页面与组件不得直接 import service，必须走 query hook | 缓存与失效逻辑被绕过 |
| `no-toisostring-slice` | 禁止截 `toISOString()`，时区会前移一天 | 日期少一天，且只在东八区复现 |
| `no-raw-viewport-check` | 禁止直读 `window.innerWidth` | 响应式分支散落各页 |
| `no-audit-fn-without-opctx` | 写审计的导出函数首参必须是 `OpCtx` | 审计缺操作人/IP |
| `no-restricted-syntax` | 业务模块禁裸调 `writeLog`；路由禁手写权限判断 | 审计与鉴权绕过中间件 |
| `no-restricted-imports` | 路由禁连库；前端禁 import 角色→权限映射 | 分层被击穿 |
| `arch:check` | 跨文件：页面必须 `React.lazy`、禁 UI 直连 axios、单文件 450 行棘轮 | 包体与单文件失控 |
| `migrate:check` | `schema.ts` 与迁移文件同步 | 部署时建表失败 |

**这条边界要写死**：门禁的判据是退出码，不是评审意见。评审能发现的问题写成规则；写不成规则的，进 §5.7 的人工复核清单，不占门禁位（P6）。

**还没对标的部分**：仓库根 `AGENTS.md` 的目录契约、`eslint-rules/` 的实际规则清单、`arch:check` 的扫描项与退出码、CI 的阻断顺序、四端隔离的具体实现、PRD 分卷与页面 ID 的漂移检查。这六项要拿一个真实多端项目逐条核，核完再改本节——不先写猜测。

## 4 七个动作

### 4.1 七次收口：拿装修打比方

装修一套房子是这么走的：量房问清需求 → 出图让人签字 → 排出工序和水电点位 → 进场搭工地 → 一道工序一道做、每道当场验收（闭水、通电） → 整体开灯走一圈 → 交钥匙、留保修单、记下这次哪儿返工。

七个动作就是这七件事，一个不多：

- **收活**：把「我想要个能管合同的东西」逼成一页纸，落到 `brief.md`。
- **校准**：把一页纸变成五张表（字段、规则、权限、审计、界面），落到 `specs/`。
- **切片**：把五张表切成一次能干完的票，落到 `tickets/`。
- **起架**：脚手架把空目录变成能跑的项目。
- **逐单**：一张票一轮，写完自测，落到 `evidence/`。
- **验收**：不是测试绿了，是人点得动。
- **交付**：交钥匙、能回滚、记一条返工。

四条性质，记住就不会误读：

1. 可跳：改一个字段不需要收活。
2. 可并：只有一个票时，校准和切片是一回事。
3. 只有「逐单」会循环：七不是工作量，是七种收口方式。
4. 判据不可跳：做完没做完，看判据，不看感觉。

不用「阶段」这个词，是因为不存全局阶段状态。动作指「你现在手上这一件事」，有开始、有产出、有一条算做完的硬标准。

### 4.2 动作卡

| 动作 | 人给什么 | AI 产出什么 | 出口判据 | 卡住怎么办 |
| --- | --- | --- | --- | --- |
| **A0 收活** | 一句话需求，可附 PRD / 原型 / 截图 | `.fde/brief.md`：做什么、谁用、输入输出、不做什么、怎么算成功 | 五问都有答案，「不做什么」至少一条 | 只问 3 个带默认值的选择题，不开放式盘问 |
| **A1 校准** | 审定采集表五页（S0 原文、S3 角色、S5 主链、S7 页面、S13 疑问），回答不超过 5 个选择题 | 采集表 v1.0 → PRD 分卷 → 原型（UI 项目）；三件套同源 | 表无空表；S15 覆盖无缺口；PRD 与原型里的编号都能回溯到表（§6.7） | 降级成轻量档：只填 S0/S1/S3/S5/S7/S11，PRD 出三卷，原型可选 |
| **A2 切片** | 确认粒度与并行意图 | 一组票：每张带执行者、阻塞边、验收谓词（3–5 条）、不碰范围、上游 mock | 每张票一次上下文能做完、完成后可演示、阻塞边无环、验收谓词 3–5 条 | 切不动说明 A1 没收敛，退回 A1 |
| **A3 起架** | 无（等待） | 脚手架生成项目、起服务、跑一次空门禁 | 首页能打开、登录可用、空项目 `check` 全绿 | 环境问题走 E0 环境向导（§8.1），不让人肉排错 |
| **A4 逐单** | 只做设计判断（界面、交互、文案），每张票不超过 2 个问题 | 按票实现，红-绿-重构，自跑门禁，写证据 | 该票验收谓词逐条有证据（测试名、截图、命令输出） | 连续两次修复失败就停：改票（拆小或改判据），不许第三次盲试 |
| **A5 验收** | 在验收卡上点 3–5 项，再点一遍页面 | 证据汇总 + 差异说明 + 演示脚本 | 卡上无「有问题」（见 5.4）、E0–E7 每道门有证据或已登记的跳过记录（见 5.3）、无未登记的已知问题 | 门禁绿但人点不动，判假绿，回 A4 并补一条 E2E |
| **A6 交付与回流** | 确认上线范围与回滚方式 | README / 部署 / 回滚三件套 + `retro.md` | 新机器按 README 能起来；retro 至少一条可执行改动 | 没有可执行改动就写「无」，不写感想 |

三条轻量档规则：

- 只有一张票的项目可合并 A1 与 A2（一张票就是全部规格）。
- 纯改动（改字段、调文案、修样式）跳过 A0，从 A1 直接进 A4，但 evidence 里要注明跳过理由。
- **跳的是准备动作，不是出口。** A0、A2 可以跳，E5、E6 不能跳。任何改动都走同一个「票 → 出口」小循环，不给修复模式单开旁路——旁路一旦存在，门就永远补不完（别人的实测，见 8.7）。
- **跳过要留痕，留痕算证据。** 跳过某动作时往 `evidence/` 写一条跳过记录（门禁编号 + `skipped: true` + 一句理由），由入口技能落盘。状态扫描认它（§5.3）；不写记录的跳过会让纯改动项目永远卡在「缺证据」上，到不了交付。

### 4.3 一次对话长什么样

这是「全程引导」的具体形态：每一轮只出现三样东西——现在在哪个动作、一个问题、一条判据。

人在空目录里说：「我要一个合同管理，能录入合同、经理审批、审批结果通知我。」

```text
现在在 A0 收活。

我先写 .fde/brief.md 的五句话，你只要回答第三句：
谁能审批？ A 部门经理 / B 任意管理员 / C 上级指定人。默认 A。

确认后进 A1，会再问 3 个字段问题。
本步判据：brief 五节齐，且「不做什么」至少一条。
```

人回「A」。到 A1 时，AI 把采集表填好，只请人审五页（原话、角色、主链、页面、疑问），审定后 PRD 与原型一起出。之后每轮同构，直到 A5 弹一张 3 项的验收卡（见 5.4），人点完就是签名。一个模块从头到尾，人回答的问题不超过 12 个。

## 5 证据与门禁

### 5.1 目录

```text
.fde/
├── brief.md
├── tickets/NN-*.md
├── evidence/
│   ├── E0-env.json
│   ├── E4-contract.json
│   └── E5-NN.json
├── handoff.md
└── retro.md
```

规格书不在 `.fde/` 里放指针：唯一真相在 `docs/specs/<name>.md`，票直接引路径加小节位置（§6.1）。多一个指针文件就多一份会漂移的真相，删。

证据文件最小字段：`gate`、`at`、`cmd`、`exit`、`artifact`、`summary`（不超过 5 行）、`by`（人或 agent 标识）。证据只能由门禁脚本或卡片工具写入（§2 P1 硬补充）；跳过记录也是证据文件，写 `mode: "SKIP"` 加理由。完整字段、31 条检查项的 ID、门级聚合规则与 JSON Schema 见[证据 schema 与门禁 ID 对照](./证据schema与门禁ID对照.md)；本节不重复定义，避免两处漂移。

`handoff.md` 最小字段：当前票编号与状态、下一张票及其所需输入、未决问题、环境特例（端口、账号、路径）。出口判据：新会话只读 handoff 加那张票就能开工，不需要翻聊天记录。

### 5.2 门禁矩阵

| 门禁 | 类型 | 判什么 | 谁跑 | 判据 | 失败退路 |
| --- | --- | --- | --- | --- | --- |
| E0 环境 | 脚本·阻断 | bun、git、端口、依赖、模板可达 | 脚本 | 6 项自检全过 | 跑环境向导，一次生成、重复可用 |
| E1 收活 | 检查 | 五问齐全、边界至少一条 | 人 + AI | `brief.md` 五节齐 | 只问 3 个选择题 |
| E2 切片 | 检查 | 无环、可演示、一上下文装得下 | 脚本 + 人 | DAG 校验通过 | 退回 E1 |
| E3 起架 | 检查 | 空项目可启动、空门禁绿 | 脚本 | `check` 退出码 0 | 换模板或查环境 |
| E4 契约 | 检查 | 采集表齐、覆盖无缺口、PRD 与原型可回溯（见 §6.7） | 脚本 + 人 | 四项差集全空 | 回 A1 |
| E5 实现 | 脚本·阻断 | 每张票的验收谓词有证据、数据断言不为零，且测试不是恒真的 | 脚本 | 证据齐 + `check` 绿 + 防假绿三条（见 5.5）+ 数据断言（金额/状态/关联，见 v1 方案 §5.8）+ 按需独立复核（见 5.7） | 改票，不盲试 |
| E6 人用 | 人卡·阻断 | 冷启动后真实后端能登录、核心旅程能走 | 人（选项卡） | 冷启动清单全过 + 卡上无「有问题」（见 5.4、5.5） | 判假绿，补 Real 模式 E2E |
| E7 交付 | 脚本·阻断 | 干净目录可起（模拟新机器）、可回滚 | 脚本 | E7 脚本复跑成功（执行体见 §5.6） | 补文档 |

**门禁编号是 ID，不是执行顺序。** 对应关系：E0 环境贯穿全程，E1↔A0 收活，E4↔A1 校准，E2↔A2 切片，E3↔A3 起架，E5↔A4 逐单，E6↔A5 验收，E7↔A6 交付。校准（E4）在切片（E2）之前发生，编号顺序不等于动作顺序，状态推导不靠编号排序（§5.3）。

**只有四道是阻断门：E0、E5、E6、E7。** E1–E4 缺了只记录、降级，不阻断。阻断门超过四道，就一定会被绕过——这是别人用 28 个版本换来的结论，不是审美。

逐条检查见 [四道阻断门检查清单](./四道阻断门检查清单.md)：每道门的 item、执行体、证据字段与假绿判例都在那份文件里；本节只保留门的定义与归属，避免同一件事写两处。

**脚本退出码三分类：PASS / FAIL / SKIP。** SKIP（环境缺、没真正检查）单列，不冒充绿——all-in-mvp 的 B033 教训：SKIP 混在 exit 0 里，门禁报全绿其实什么都没查。证据文件的 `exit` 记原始退出码，`summary` 必须写明 SKIP 原因（§14）。

### 5.3 状态怎么推导

分两层，不用「按编号找第一个缺证据的门」这种线性扫描——那会把阶段思维从后门请回来，而且门禁编号与动作顺序错位（§5.2），线性扫描会指错路。

**宏观位置看动作产物**：无 brief → A0；brief 齐无规格 → A1；规格齐无票 → A2；票齐项目未起 → A3；项目已起 → A4；全部票 done → A5；验收过 → A6。跳过记录（`skipped: true` + 理由）算该动作的产物。

**A4 内部只看票前沿**：找出所有 todo 且阻塞已完成的票（§6.2），门禁编号在这里不参与调度。票的 done 由证据推导，不手写（§6.2）。

全部齐了就是可交付。这一条替代 `current_phase` 与 `current_step`，好处是不需要问「上一步完成了吗」，坏处是证据可伪造——所以证据必须由脚本自己写出（§2 P1 硬补充），含命令、退出码与时间戳，人工确认要留签名行。

### 5.4 人验收用选项卡，不用口头确认

口头「确认了」不是证据：人在赶时间时会点头，AI 又会把点头当成通过。所以凡是要人判断的地方，一律弹一张卡，人选完，卡的结果直接写成证据。这就是签名行，也是 E6 唯一认的东西。

**三类卡**

| 卡 | 什么时候出 | 选项 | 结果落到哪 |
| --- | --- | --- | --- |
| 决策卡 | A0 收活、A1 校准 | 单选或多选，每项带默认值与影响说明 | `evidence/decide-*.json` |
| 确认卡 | A5 验收（E6） | 逐项：通过 / 有问题 / 看不懂 | `evidence/E6-<card>.json` |
| 打回卡 | 任何动作发现问题 | 原因四选一 + 一句补充 | 自动开一张新票，回 A4 |

**确认卡长什么样**

```text
验收卡 E6-01（合同管理 v1）  3 项，约 2 分钟

1. 状态规则
   打开 docs/specs/contract.md#状态规则
   草稿 → 生效 → 归档，归档后不可编辑。这符合你要的吗？
   [ 符合 ] [ 不符合 ] [ 看不懂 ]

2. 金额校验
   打开 /contract 新建页，输入 0、负数、12 位小数
   这三种都被挡住了吗？
   [ 都挡住 ] [ 有漏的 ] [ 没试 ]

3. 审批通知
   打开右上角铃铛
   审批通过后 5 秒内出现「合同 XX 已生效」吗？
   [ 出现了 ] [ 没出现 ] [ 没测 ]
```

**卡从哪来**：不是 AI 临场编问题，是从这张票的验收谓词和五要素里的业务不变量倒推出来的。一张卡每轮不超过 3 项（`ask_user_question` 的实际轮次上限在 P0 前实测，见 §11.2），票谓词有 5 条就分两轮；每项必须指到一个能打开的东西——文件行号、页面路由、截图、测试名。指不到的项，说明这条验收谓词写虚了，回 A2 改票。

**防闭眼点**

- 不预选，没有「全部通过」这种一键盘
- 每项都留「看不懂 / 没试」。允许不知道，比假装知道有价值
- 填空抽查是可选项，默认关闭：只在怀疑闭眼点（如整卡秒过、连续多卡全通过）时启用，抽 1 项让人说出当前值，答错本轮不算过。白皮书说人的心流用在设计决策与抽查的刀刃上，不是用来答题；默认不给人加这道负担
- 卡里记 `at`、`by`、`choice`、`note`：谁点的、几点点的、有没有改过，全留痕

**三种形态，按规模选**

| 形态 | 用在 | 成本 |
| --- | --- | --- |
| 对话内选项卡 | 默认，3–5 项 | 零 |
| 生成的验收页（本地 HTML，勾完导出 JSON） | 10 项以上、要比对截图 | 一次性模板 |
| 终端向导脚本 | 环境与部署类（E0、E7） | 一次性脚本 |

对话内选项卡用 DSH 的 `ask_user_question`：单选、多选、每项带一句说明。方案按每轮不超过 3 项设计，多出来的分下一轮；它的实际轮次上限与技能常驻行为在 P0 前实测（§11.2），不把未验证的宿主能力写进判据。

**失败怎么走**

- 选「看不懂」：先解释，再问同一张卡，不新开卡。同一处连续两次「看不懂」，说明这处没设计明白，转成 A1 的补充问题
- 选「有问题」：出打回卡，写清现象，自动开一张新票，回 A4
- 整张卡没人回答：不算通过。E6 留空，进度停在这，别用「默认通过」兜底

### 5.5 冷启动与防假绿

这两条都是花钱买来的，写进来能省一次事故。

**冷启动清单**是 E6 的执行体，不依赖任何测试结果：

1. 删掉数据库文件，模拟全新部署
2. 启动后端，确认种子日志里的账号数量正确
3. 启动前端，确认端口与配置一致，没有漂移
4. 用登录页上真实存在的账号逐个登录，数量与种子一致
5. 确认每个角色登录后落到正确页面
6. 确认被禁用账号被拒、需改密账号弹出改密页（注意 starter 能力缺口，见下方说明）
7. 打开 console，记录所有报错，A 类阻塞项清零
8. 核心旅程的异常分支走查一遍（403、409、空态、超长输入），每条须有可复现的触发方式；造不出数据就登记为已知问题，不算测过（借 mvp-verifier 的「造数缺失即 BLOCKED」，§14）

**第 6 项超出 参考脚手架 现状**：禁用拒登、强制改密是 all-in-mvp 的验收约定（kf-mvp-test-e2e 与 mvp-verifier），starter 只实现了 change-password 路由，users 表没有 disabled 字段（实测，§14.4）。P0 前二选一：给 starter 补这两个字段，或把第 6 项裁剪为「需改密账号弹出改密页」。清单必须与脚手架实际能力一致，否则 E6 永远红。

**E2E 双模**：Mock 模式只用于开发阶段的快速反馈；交付前必须用 Real 模式跑一遍——真实后端、真实数据库、真实密码校验。只跑 Mock 的绿灯不算绿。E2E 与人验收共用同一套后端，这是对「92 条用例全绿、人一登录就报密码错误」（§1.5）的根治。

**种子与造数约定**（直接复用 starter 的实测资产，§14.2）：账号唯一真源（`seed-users.ts`）；固定主键 + `onConflictDoNothing` 幂等播种，可重放；种子脚本在 production 拒绝执行；dev-only 造数端点（`dev/push`、`dev/reset`）在非 development/test 环境一律 404。种子不手填——手填的种子是第二份真相，冷启动一删库就露馅。

**防假绿三条**，写进票的出口判据：

1. **seam 预确认**：测试只写在事先与规格书确认过的公开边界上，每个 seam 注明「抓什么、漏什么」
2. **反恒真断言**：期望值必须来自独立真相源（规格书、手工算例、已知正确字面量），不许用和实现同样的方式重算期望值
3. **测行为不测实现**：只经公开接口观察，mock 只打外部边界

一句话：脚本能查覆盖率，查不出恒真断言；只有写测试那一刻的规则能防。

### 5.6 E7 执行体：干净目录复跑

E7「新机器可起」必须绑脚本，否则就是散文门（§2 P6）。试点期没有第二台机器，用干净目录模拟新机器，脚本按序做六步：

1. 把交付标签 clone 进全新临时目录（不带 node_modules、不带 .env、不带数据库文件）
2. 按 README 装依赖，记录命令与退出码
3. 跑 `check`，全绿
4. 按 README 初始化数据库与种子、起服务
5. 用种子账号登录并走一遍核心旅程（复用 E6 的冒烟脚本）
6. 回滚验证：按 README 的回滚步骤恢复到上一版本，再启动一次

任何一步失败即 E7 红，退路是补 README——这类失败大多不是代码错，是 README 漏了只存在于作者脑子里的步骤。脚本自己写 `E7.json`（§2 P1 硬补充）。真实新机器或容器验证放 P2，试点期以干净目录复跑为阻断判据。

交付包同时跑内网坐标扫描（复用 all-in-mvp 的 `check-private-refs.ps1`，见 §14）：内网地址、账号、令牌路径写进交付物，既是死链又是暴露面。注意它的三态退出码：0=通过、1=失败、2=没扫到（SKIPPED 不等于通过）；豁免必须同行写 `R040-allow: 理由`，无理由的放行标记仍判失败。

**证据写入守卫（可选加固）**：DSH 支持写入钩子时加一条——检测到对 `.fde/evidence/` 的写入且写入者不是门禁脚本，就注入报错、要求改由脚本重跑。all-in-mvp 的 `quality-gate-hook.ps1` 是现成样例（matcher `Write|Edit|MultiEdit`，stdin 读 `file_path`，路径命中 → stderr 注入门禁指令 → exit 2，写入本身不回滚）。注意它的实测教训：钩子要会话重启后才生效，所以守卫是加固不是依赖——没有钩子，「agent 不写证据」的规则仍在，靠独立复核（§5.7）兜底。

### 5.7 独立复核与测试静态检查

实现者自测查不出自己的盲区。all-in-mvp 的 B020 血案：修复者既写代码又自查，Checkbox 布局异常漏修，直到用户二次点名才发现。借两个机制，都按轻量档用：

**独立复核（抽查，不是全量）**：派干净上下文的复核子代理，只读票 + 规格书片段 + 证据，只审不改——重跑验收谓词、核对防假绿三条。触碰共享契约、权限、认证的票必须复核；其余按三分之一抽查（白皮书抓大放小：全量复核的成本会压垮单人交付）。发现分 P0（阻断，清零才算过）/ P1（记录，≤2 条）；同一票打回上限 3 轮，超了转人介入，不让两个代理循环打架。复核者不修代码，修复回原执行者——运动员兼裁判是 B020 的根因。

**测试静态检查（E5 前置清单）**：跑测试之前先查四件——测试文件存在且非空；测试引用的 API 路由在契约里真实存在；fixture 字段类型与 schema 一致；每条业务不变量至少有一条负例（§8.3）。前三件可脚本化（参考 all-in-mvp 的 check-api-endpoints 思路，§14），第四件脚本计数、不足转人卡确认。这一层拦的是「测试没测真接口」，比跑一遍 E2E 便宜得多。

## 6 票

### 6.1 票不是需求文档

票只干两件事：**派给谁干**、**拿什么算完**。它不定义界面长什么样。

| 层 | 回答什么 | 载体 | 谁写 |
| --- | --- | --- | --- |
| 需求原文 | 客户到底怎么说的 | `.fde/brief.md` + 采集表 S0 | 人一句话，AI 记录 |
| 事实 | 有哪些角色、页面、字段、规则、验收 | 采集表 16 张（`docs/采集表/<name>.xlsx`） | AI 填，人审定 |
| 裁决 | 为什么这么做、冲突以谁为准 | `docs/specs/`（PRD 分卷） | AI 写，人确认 |
| 样子 | 长什么样、点下去发生什么 | `prototype/` | AI 做，人试用 |
| 派工 | 这次让哪几条从「没有」变成「能用」 | `.fde/tickets/NN.md` | AI 拆，人点头 |
| 证据 | 凭什么说做完了 | `.fde/evidence/NN.json` | 脚本加人卡 |

一条规则管住全部：**一处定义，处处引用。** 界面细节的唯一定义在采集表 S7；PRD 只引用 `REQ` 编号，票只引用 `REQ` 加验收谓词，原型只引用页面 ID。任何一层再抄一份字段表，就是第二份真相，改一处必忘另一处。

票里出现的元素级编号（如 `F-03/a`），是 S7 行内元素的引用标签，不新增内容：S7 那一行的操作清单第 2 项，就是 `F-03/b`。行内容改了，同一版本内编号重排、不跨版本复用。

界面的细节长这样（示例取自 S7 一行拆出的元素）：

| 编号 | 页面 | 区块 | 元素 | 类型 | 行为 | 权限 | 空态 | 错误态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| F-03/a | 合同详情 | 操作栏 | 「审批通过」 | 主按钮 | 弹确认框后调 approve | admin | — | 409 提示状态已变更 |
| F-03/b | 合同列表 | 状态列 | 状态徽标 | 行元素 | 草稿灰、生效绿、归档深灰 | 全员 | 显示占位符 | — |
| F-03/c | 合同详情 | 表单 | 金额 | 输入框 | 必填、大于 0、两位小数 | admin 可改 | — | 红字并阻止提交 |
| F-03/d | 全局 | 顶栏铃铛 | 通知条目 | 列表项 | 审批通过后推一条 | 审批人 | 无通知时不显示 | 推送失败重试一次 |

票写「本次做 F-03/a、F-03/b、F-03/d」，不抄字段表。

**但也不能只写编号**：执行者拿到 F-03 要去翻整份规格，上下文立刻变大，还容易漏。票里要带的是「这次要验的那几条**可判定事实**」——引用加最小谓词，不是复制全文。

白皮书说票里包含数据设计、接口设计、前端设计、编码、联调、测试，这里不冲突：票**要落这些产物**，但**不抄这些设计的全文**。产物在规格书和代码里，凭据在票上。

### 6.2 票模板

```text
# 07 审批生效（F-03）

执行者：fde-逐单（同屏子代理）或 sa-worker（引擎派发，见 §15）
输入：本票 + specs/contract.md#F-03 + fixtures/contract.json
状态：todo / doing（可手写，是意图）；done 由扫描从证据推导，禁止手写
阻塞：05（列表页）、06（详情页）
授权：业务方张三批准；可改 apps/web 与 packages/shared；不动契约字段、不加依赖、不改 CI；diff 超 200 行停下问
本次让哪些从「没有」变「能用」：F-03/a 主按钮、F-03/b 状态列、F-03/d 通知
不碰：批量审批（另开一张）
演示方式：点哪个页面、看哪条数据

验收谓词（3–5 条，每条一条命令或一次点击）：
1. 草稿合同详情页有「审批」按钮；已归档的没有
2. 点通过后 GET /contracts/:id 的 status = active
3. 非 admin 调 POST /contracts/:id/approve 返回 403
4. 审批通过后 5 秒内铃铛出现一条通知

上游 mock：接口、字段、样例数据；不可用时的替代品
门禁：本次必须跑哪几道
证据：evidence/07-*.json
签署：脚本签（check 退出 0）+ 人卡 E6-02 第 2 项
```

三处是关键：**执行者**写技能或子代理，不写模型名，换模型不动票；**不碰**划边界，没有边界的票会被顺手改别的模块；**签署**说明这张票由谁点头。

| 票类型 | 执行者 | 谁签 |
| --- | --- | --- |
| 实现票 | 干净上下文的子代理（`fde-逐单`） | 脚本（`check` 退出 0） |
| 验收票 | 人 | 人（在验收卡上点选，见 5.4） |
| 修复票 | 子代理，由打回卡自动生成 | 脚本加同一张验收卡复检 |

「人」只在这两处出现：拍板（A1 的选择题）和验收（A5 的卡）。其他位置写「人」，都是把该自动化的事甩给了人。

票是派工意图的唯一载体，完成状态由证据推导（§2 P1）：调度就是「找出所有 todo 且阻塞已完成的票」，恢复就是读目录。一张票算 done，当且仅当它的证据存在且通过；手写 done 无效，扫描不认。不建 `pipeline-state.json` 一类的全局状态文件——那是又一份会撒谎的真相。

本节是最小模板。卡号与波次、节拍与串并、三阶段勾选、交付回执的完整写法见[《all-in-fde v1 技能实现方案》](./all-in-fde-v1-实现方案.md) §4；那张表才是派工的唯一真相。

### 6.3 粒度与验收条数

一次上下文装得下（经验值：单票改动不超过 6 个文件）、完成后可演示、阻塞边真实。

验收谓词 3–5 条。超过 5 条，票切大了；少于 3 条，可能两张该合并。

切法一句话：**这张票做完，能不能当着人点一遍？** 能，就是竖切；不能，说明切法是横的——列表字段一张、主按钮一张、弹窗字段一张，那是把一条竖线剁成三段，每段都演示不了。

### 6.4 并行与串行

没有共同文件、没有共同契约变更的两张票才并行。共享契约变更单独出票，先做，其余票等它。宽重构按 expand–contract 拆三张：加新形态 → 分批迁调用点 → 删旧形态。

### 6.5 时段与模型路由

| 活 | 模型档 | 时段 | 理由 |
| --- | --- | --- | --- |
| 切片、验收判定、代码审查 | 强 | 任意 | 判错的代价高于算错的代价 |
| 批量改、长文、E2E 跑批 | 弱 / 便宜 | 低价时段 | 可重跑，可等待 |
| 引导对话 | 中 | 任意 | 要短、要稳，不追求上限 |

缓存友好三条：会话内 `AGENTS.md` 前缀不变、`.fde/` 路径不变、不中途换工具。命中率最高的是「同一会话做完同一张票」。细则借 all-in-mvp 的 shared-prefix 规则（§14.2）：前缀逐字相同（包括空格和换行）、前缀在前、工具列表按字母序做排序防御、版本号全文件同步。这些是通用前缀缓存规则，不绑特定模型厂商。

### 6.6 执行者描述文件（白皮书五要素）

白皮书「Agent 描述文件：输入，输出，流程，约束，工具」说的是**执行者（子代理）的定义**，不是票。票只写执行者名字（§6.2），五要素落在执行者描述文件里，一个执行者一份：

```text
# fde-逐单（实现执行者）
输入：本票 + 票引用的规格书片段 + fixtures；不读整份规格，不读别的票
输出：代码 diff + 门禁脚本写出的证据 + handoff 增量；返回只给摘要（默认 ≤1500 token）
流程：读票 → 核对验收谓词 → 红（先写失败测试）→ 绿 → 重构 → 跑票指定门禁 → 由脚本落证据
约束：不碰票「不碰」范围；连续两次修复失败即停并上报；不手写证据；不顺手扩范围；设计问题每张票 ≤2 问
工具：DSH 的文件、终端、浏览器工具 + 票指定的门禁脚本；开工先加载 `ponytail`（full 档，见 §7.2），除此之外不加载其他技能
```

验收执行者是人（§6.2），不需要描述文件；修复执行者复用这份文件，输入换成打回卡。换模型只动 §6.5 的路由，不动这份文件——这正是白皮书「分工分得好」的落点：描述文件定义岗位，票派活，路由选刀。

### 6.7 需求采集表：A1 的工件，也是全流程的脊柱

一段话变成系统，中间缺一层**人能逐格核对的事实表**。A1 校准的产物是三件套，不是一份草稿：

| 工件 | 回答什么 | 谁审 | 变化速度 |
| --- | --- | --- | --- |
| 采集表 | 事实：有哪些角色、页面、字段、规则、验收 | 人逐格核（只看五页） | 每天 |
| PRD 分卷 | 裁决：为什么这么做、冲突以谁为准 | 人确认口径 | 每周 |
| 原型 | 样子：长什么样、点下去发生什么 | 人试用 | 每周 |

表是事实，PRD 是裁决，原型是样子。三层各写各的，不许互相抄：PRD 引 `REQ` 编号，原型引页面 ID，票引 `REQ` 加 `AC`。

模板、十六张表的用途、填写铁律见[需求采集表模板](./需求采集表模板.md)，空白文件是 `skills/all-in-fde/assets/需求采集表-空白模板.xlsx`。PRD 怎么分卷（00a/00b/01/02/03–07/08a–08b/09/10/11/12）也在那份文件的附录 A。本节只说架构，不抄表目录。

**人只审五页**：S0（原话有没有被改）、S3（角色对不对）、S5（主链顺不顺）、S7（页面全不全）、S13（疑问有没有被藏起来）。其余抽查，单项目不超过 30 分钟。这是白皮书「人的心流用在决策与抽查」的落点。

**三处引用**

- 票挂 `REQ-`：A2 切片的输入是 S7 的页面行，「本次让哪些从没有变能用」写 `REQ-C01`，不写「合同详情页」。
- 验收引 `AC-`：票验收谓词从 S11 取，不许现编。
- E6 走 S5：冷启动的「核心旅程」取主链前三步，不改写。

**E4 四查**（脚本做，人只看差集）

| 查什么 | 不过怎么办 |
| --- | --- |
| 表齐不齐（按档看） | 补表 |
| S15 有没有未覆盖项 | 补行或记 S13 |
| PRD 的编号能不能回溯到表 | 退回改表或改 PRD |
| 原型页面 ID 与 S7 对不对得上 | 同上 |

**三档，别一刀切**：轻（六张表、三卷 PRD、原型可选）／标准（十六张、分卷、原型必做）／重（十六张加端 × 角色细化、多端原型）。轻量档缺的表在 S15 写「本档不适用 + 理由」，不算缺口。不许默认走重档——表填得再全，人审不动就是负担。

**回写环**：PRD 或原型发现缺口 → S15；新问题 → S13（带建议方案）；人拍板 → S14 记决议 → 回写受影响行 → 改回写状态列（已回写 / 部分回写 / 待回写）。表更新升版本，PRD 分卷头部同步版本号。

**这层最容易出的三个错**

1. AI 把推断写进事实列。对策：推断只能进 S13 的「AI建议方案」，事实列留「待确认」。
2. 表填完没人审就生成 PRD。对策：A1 的出口判据就是审定痕迹——五页的「客户核验」列全为已核验。
3. 三件套各改各的。对策：E4 的反向校验；PRD 里的编号在表里找不到就退回，不解释。

## 7 技能包清单

初始只有一个技能加七个 reference 文件。只有满足三条才升格为独立技能：有独立触发词、有独立完成判据、会被入口之外的地方调用（例如 CI 或人）。

| 名字 | 形态 | 触发 | 产出 |
| --- | --- | --- | --- |
| `all-in-fde` | user-invoked 技能 | 用户点名 | 地图 + 下一步 + 判据 |
| 收活 / 校准 / 切片 / 起架 / 逐单 / 验收 / 交付 | `references/*.md` | 入口内部加载 | 对应产物 |
| `fde-slice` | model-invoked 技能 | 「拆一下」「切票」 | `tickets/` |
| `fde-verify` | model-invoked 技能 | 「验收」「跑门禁」 | `evidence/` + 验收卡 |
| `ponytail` | 外部技能（v5.3.3，MIT） | A4 开工时由执行者加载 | 更小的实现 diff |
| 导出 | 复用 `kf-markdown-to-docx`、`kf-markdown-to-xlsx` | 交付时 | docx、xlsx |

首轮只升格两个：`fde-slice` 是判断活，值得独立触发；`fde-verify` 会被人和 CI 同时调用，必须有独立入口。

**明确不建**：`fde-frontend`、`fde-backend`、`fde-db`。这些是脚手架的领域，再造一层只会让触发词打架、让常驻成本翻倍。

**总量上限**：技能不超过 8 个，常驻合计不超过 500 行，单个 `SKILL.md` 正文不超过 200 行。超了先删再加。入口启动时自检三样——文件在、frontmatter 完整、版本号与 reference 对得上；任何一项失败就报错并给修复命令，不许静默降级（别人的技能曾因 frontmatter 解析失败在列表里静默消失）。frontmatter 校验直接复用 all-in-mvp 的 `check-skill-frontmatter.ps1`（§14），不重写。

### 7.1 触发边界：评测用例先于正文

入口技能最大的失败不是写得差，是该跳出来时没跳出来、不该跳出来时抢了别人的活。P0 写正文之前先定评测用例：至少 3 条正例 + 3 条负例，description 跑通全部用例才动工；此后每次改 description 重跑一遍。

与相邻能力的边界：

| 邻居 | 边界判据 |
| --- | --- |
| all-in-mvp | 多模块、要多代理并行流水线的 MVP → all-in-mvp；预计票 ≤5 张、用户非工程人员、要全程引导的小系统 → all-in-fde |
| 脚手架领域技能 | 已在 参考脚手架 项目里加一个功能 → 直接用脚手架的 business-feature-builder，不走 fde 入口 |
| 纯咨询 / 其他体裁 | 「React 和 Vue 哪个好」「帮我写个 PPT」→ 不加载交付技能 |

评测用例示例：

- 正例：「我想要个能管合同的东西，我不会写代码」／「把这句话需求变成一个能用的系统」／「继续上次那个项目」（恢复场景）
- 负例：「做个多模块电商 MVP，后端并行开发」（应去 all-in-mvp）／「给现有项目的用户表加个字段」（应去脚手架领域）／「帮我审阅这份长文」（应去文档技能）

负例被抢走时收紧 description，不加正文——正文治不了路由病。

### 7.2 外部技能怎么接：以 ponytail 为例

有些能力不值得自己写，装现成的更划算。判据三条：**只回答一个判断**（不抢流程）、**输入输出能塞进现有动作**、**卸掉不影响交付**。

`ponytail`（[DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)，MIT，v5.3.3）是第一个例子。它管「怎么写得更少」，不管「做什么、算不算完」。

| 项 | 落法 |
| --- | --- |
| 装在哪 | `skills/ponytail/`，再 `node scripts/sync-runtime.mjs` 同步到 `.dsh/skills/` |
| 何时加载 | A4 逐单开工第一件事，`full` 档；A1、A2 不加载——那两步定做什么，不是怎么写 |
| 装之前改什么 | 只把 `description` 换成中文触发描述，正文逐字不动；改动记进 `PROVENANCE.md` |
| 与门禁的边界 | 写在 `references/fde-usage.md`：规格书、权限、审计、测试、架构门禁不可省；冲突时门禁优先，并在票记一行「因门禁保留 X」 |
| 产出要求 | 结尾一到两行说明跳过了什么、没查什么；捷径写成 `shortcut: <限制>, <何时升级>`，进 retro 收进债务 |

外部技能不占「技能不超过 8 个」的名额——那条约束管 fde 自己的分支，不管装来的工具。但它们占常驻：model-invoked 技能都有一段 description 在列表里。所以装机标准只有一条：**说得出它在哪个动作里触发**，说不清的不装。

它最容易被误用的地方，是把「精简」当成删校验。上游自己写了「绝不删信任边界上的校验、错误处理、安全、无障碍」，我们再加一条更硬的：**门禁说了算**。这条边界写进引用文件，不指望模型每次自觉。

## 8 失败模式与对策

### 8.1 环境门槛（最大风险）
白皮书说「会用电脑」，脚手架要 bun + git + 终端。这个落差必须在 E0 解决（环境向导是 A3 卡住时的退路，不是第八个动作）：一次性的环境向导，把只有人才能做的部分（装运行时、开端口、填密钥）做成可重复脚本，其余全自动。判据不是「装好了」，是「空项目能起、能登录、能跑空门禁」。

### 8.2 假绿
测试全过，人一碰就卡。对策：E6 不可省；每个模块至少一条从登录到核心动作的 E2E；种子数据必须脚本生成、可重放，不手填——具体约定（单源、幂等、生产守卫、dev-only 造数端点）见 §5.5，E2E 与验收共用同一套后端。

### 8.3 用例不全
AI 写的用例覆盖它想到的分支，不覆盖它没想到的。对策：用例从 5 要素里的「业务不变量」推出来，不从代码推；不变量有几条，至少写几条负例。**再加一条**：只断页面能用、不断数据对不对的用例，算半个用例——金额、汇总、状态、编号这些必须落到接口或库上的断言（详见 v1 方案 §5.8）。

### 8.4 技能堆砌
技能越多，触发词越打架，常驻越贵。对策：P3 + 升格三条 + §7.1 的负例评测。季度修剪（删一个没人调的 reference）与季度成对评测是运营期（P2）动作，不带进 P0/P1——试点期只做 P1 验收那一次成对评测，先证明增益，再谈修剪。

### 8.5 上下文超载
一张票塞太多，模型后半程质量下滑。对策：单票不超过 6 个文件；跨票必须清上下文或换会话；handoff 只写「下一张票需要什么」。

### 8.6 状态伪造
人会顺手勾「完成了」。对策：证据必须含命令与退出码，且只能由脚本写出（§2 P1 硬补充）；人审留签名行（时间 + 姓名缩写）；retro 专门复盘「哪条证据事后被证明是假的」，并把它升级成脚本检查。retro 条目用 PLAYBOOK 格式：现象–根因–教训–落地，每条绑一个门禁编号或明确标「不绑」；同一条经验至少在两个项目出现才升格为规则，防止一次偶发事故把规则库撑肥（§14.2）。

### 8.7 散文门禁与旁路
门禁写成 MUST 散文，模型照读不照做；再给修复模式单开一道小门，于是所有改动都从小门走。对策：P6 每条门禁绑脚本或绑人卡；阻断门只留四道；任何改动走同一个票循环，不设特殊模式。

### 8.8 口头约定与真相源漂移
「端口用 2222」「账号固定三个」只存在于对话里，第三次会话就丢了。对策：人提的每条约束 30 分钟内落到一个文件里并带断言；每类信息只有一个权威位置——`brief` 不重复 `spec` 的字段，票不重复 `spec` 的不变量，证据只存结果不存规则。

### 8.9 控制层单点
入口技能的一个字段写错，整套流程静默失效；改了规则要重启才生效。对策：入口启动自检（文件、frontmatter、版本号），失败要吵；规则只存一处，其他地方引用编号。

## 9 度量

| 指标 | 定义 | v1 目标 |
| --- | --- | --- |
| 首次可验证时间 | 从一句话到第一次 `check` 绿 | ≤ 2 小时 |
| 人工决策次数 | 单模块人回答的问题数 | ≤ 12 |
| 门禁一次通过率 | 首次跑 E5 即绿的比例 | ≥ 60% |
| 返工率 | 同一票重开次数 ÷ 票总数 | ≤ 0.3 |
| 非工程人员独立完成率 | 无工程师在场完成交付的比例 | 试点期 ≥ 50% |
| 单模块 token | 输入 + 输出 | 记录基线，每季降 15% |
| 技能增益 | 固定评测任务集（≥3 条真实小需求，P0 前定死）上，带技能与不带技能的完成率差 | ≥ 30 个百分点 |
| 入口常驻行数 | 入口 `SKILL.md` 正文行数（description 另计，约百 token） | ≤ 200 |
| 散文门禁占比 | 阻断门（E0/E5/E6/E7）中无执行体的门 ÷ 4；人卡算执行体，E1–E4 检查项不计入 | 0 |
| 完成时间 p50 / p95 | 从收活到 `report=ready`（主口径）与到交付（端到端），样本报量与删失数；引擎自动采集，跟做档手工抽样 | 记录基线，p95 逐季降 |
| 每单打扰次数 | 发给人的消息数 ÷ 票总数；引擎自动统计 | ≤ 2 |
| 观察校准度 | 观察档里被判「本来会接受」的票，人后来真接受的比例 | ≥ 80% 才准开派发档 |
| 准入漏斗 | 收到事件数 → 规则筛掉 → 进模型 → 接受，四段计数 | 规则筛掉比例越高越省 |

## 10 分步实施

**P0（1 周，可演示）**
先写触发评测用例（§7.1），再写入口技能 + brief / tickets / evidence 三件套 + 接脚手架。四道阻断门定死并脚本化（E0、E5、E6、E7，E7 执行体见 §5.6），其余只记录不阻断。跑通一个真实小项目：合同管理，一张表、一个审批、一条通知。
验收：没写过代码的人，在有人旁听但不插手的条件下，2 小时内得到一个可登录、可增删改查、门禁全绿的系统。

**P1（2–3 周，可复制）**
七个 reference 写完；E0 环境向导；E6 的 E2E 与种子数据脚本；retro 模板；三个试点项目。接一个本地投递目录作为事件源，用观察档跑满 10 张票（§15.3），不改交付方式。
验收：三个项目里至少两个由非工程人员独立完成；门禁一次通过率不低于 60%；并用一次成对评测（带技能与不带技能）证明增益，而不是只看试点反馈。

**P2（1–2 月，可运营）**
经验回流（每个项目的 retro 变成下个项目的一条规则或一道门禁，格式借 all-in-mvp 的 PLAYBOOK 血案条目，见 §14）；多端与导出；成本看板（按时段与模型统计 token）；技能自身的季度修剪与季度成对评测（从 §8.4 移入）；E7 升级为真实新机器或容器验证。观察校准度达标后开派发档，同时上线看门狗三判据（§15.6）与预算熔断。

## 11 用什么来编写这个技能

这是本方案里唯一关于工具的决定，单独说清楚。

### 11.1 三个交付物，三条生产线

读者不同，生产线也必须不同。

| 交付物 | 读者 | 体裁要求 | 生产线 |
| --- | --- | --- | --- |
| 白皮书、引导手册、验收报告模板 | 人（客户、试点用户） | 章节、编号、术语、可打印 | all-in-md |
| 技能骨架、评测集、打包 | agent 加维护者 | 目录约定、frontmatter、能对照评测 | skill-creator |
| `SKILL.md` 正文、`references/*.md` | agent | 短、判据化、指针化、每轮都付费 | writing-for-agents 五个写法 |

### 11.2 写技能本身：用 skill-creator，只用它一半

结论：骨架和评测回路用它，命令和打包格式不照搬。

它薄的地方：目录就是 `SKILL.md` 加可选的 `scripts/`、`references/`、`assets/`，再加一条「正文不超过 500 行、按需加载」。这部分手写半小时就够；它默认 Claude 的安装路径和 `.skill` 包格式，DSH 用不上，照搬会卡在安装与打包上。

它厚的地方，恰好是现在最缺的三件：

1. **对照评测**：同一条任务跑两个子代理，一个带技能、一个不带，比通过率、耗时、token。这是唯一能回答「有技能比没技能强多少」的办法，也能挡住「技能写了但没人用」。
2. **触发描述优化**：造 15–20 条该触发与不该触发的查询——近似的、含糊的、会被别的技能抢走的——反复改 `description` 看命中率。入口技能最大的失败不是写得差，是该跳出来时没跳出来。
3. **人工评审页**：把每次迭代的产出并排摆给人看，收完反馈再改。它比「我觉得挺好」可靠。

在 DSH 里怎么落：

| 它的做法 | 我们的替代 |
| --- | --- |
| 两个子代理跑 with-skill / baseline | DSH 的 subagent 直接复刻，不用它的脚本 |
| `run_loop.py` 调 `claude -p` 优化描述 | 换成子代理循环，或人工跑 20 条记命中 |
| `.skill` 打包 | 目录安装（`~/.dsh/skills/<name>`）加一个压缩包 |
| 评测集 `evals/evals.json` | 格式直接沿用，字段不动 |

一处技术确认（**待实测，不作既定事实**）：材料称 DSH 支持 `disable-model-invocation`，`modelInvocable: false` 的技能只从 `/` 菜单进、不占模型上下文。此说法未在本机验证过。P0 前在 DSH 上实测两件事：① user-invoked 技能是否真的零常驻（注意：多数宿主的技能 description 仍会进启动列表，约百 token/技能，「零常驻」通常指正文）；② `ask_user_question` 每轮可问几项。实测不成立就改入口为 model-invoked 加短 description，并重算常驻成本——判据不能建立在未验证的宿主能力上。

### 11.3 写给人看的部分：all-in-md（standard 档，2 轮审查）

管白皮书、引导手册、验收报告模板，不管 `SKILL.md`。理由：

1. 它是本机唯一为长篇中文正式文档设计的技能，带需求规格书、三视角并行起草、确定性脚本校验（编号、交叉引用、占位符、表格列数）、词汇剂量门禁。
2. 它的门禁正好压在这类文档最容易出事的地方：编号错、引用断、术语漂移、AI 味。
3. 它已经内置与 `ai-flavor-guard`、`kf-markdown-to-docx` 的联动，导出 docx 不用另搭一条链。

不用 deep 档：deep 是三轮审查加整篇重写，对内部方案过重。用 standard + 2 轮，等评审意见回来再升。

### 11.4 正文怎么写：writing-for-agents 五个写法

`SKILL.md` 给 agent 读，成本结构和给人读的完全不同：每个字每一轮都在花上下文。skill-creator 管骨架与评测，不管这段内容判断，所以按 mattpocock 的五条来：

1. 指针措辞决定触发——description 写「什么时候用」，不写「这是什么」。
2. 两种负载分开算——常驻上下文与人的记性；入口优先 user-invoked，description 常驻约百 token、正文零常驻（以 §11.2 实测为准）。
3. 信息分层——步骤进正文，规则进 reference，按分支披露。
4. 完成判据——每个动作以可检查的条件收尾，不写「理解清楚后继续」。
5. 领词——用「票」「证据」「前沿」这类已有词，不造新词。

这五条固化成 `references/writing-skills.md` 放进仓库：它比任何外部技能都更贴近这个场景，也不依赖外部技能是否安装。

### 11.5 配套四件

- `ai-flavor-guard`：词汇剂量。技术方案档（`tech`），起草阶段 `--gate warn`，终稿 `--gate error`。
- `kf-markdown-to-docx`：白皮书出 Word。模板沿用现有 docx 的样式，避免版式返工。
- `excalidraw-skill`：架构图与七动作流程图。产出 `.excalidraw` 源文件加 PNG，后续能改。
- `kf-kb-envoy`（可选）：把试点项目的 brief、spec、retro 收成知识库，供下个项目检索。没有就不建，别为流程而流程。

### 11.6 不推荐用它们做这件事

| 技能 | 为什么不用 |
| --- | --- |
| `ppt-master` | 产出是演示文稿；方案要先能逐条评审，不是先好看 |
| `kf-markdown-to-xlsx` | 只适合把清单转表；正文写成表格会丢论证 |
| `office` / `office-docx` 直写 | 手写 OOXML 做不了编号与引用校验，改一次错一次 |
| `kf-kb-envoy` 单独用 | 它是摄入与检索，不产出论证 |
| `skill-creator` 全流程照搬 | 路径、打包、描述优化都绑 Claude；只借流程，不借命令 |

### 11.7 产物净化门：方案可以脏，技能必须干净

两份东西两套标准，别混：

| | 方案（本文） | 技能产物 |
| --- | --- | --- |
| 读者 | 我加施工的人 | 外部用户 |
| 内网地址、本机路径、内部项目名 | 允许，方便施工 | 一律不许 |
| 内部技能名、仓库命名空间 | 允许 | 一律不许 |
| 公开仓库链接 | 允许 | 允许 |

**产物的范围**（按用途判，不按目录名猜）：`skills/all-in-fde/**`（SKILL.md、references、scripts、assets，含随技能分发的空白采集表）、`tools/build-requirement-template.py`（表格的生成器，本地工具目录）。

把关用命令，不靠眼看：

```bash
node scripts/check-public-artifacts.mjs        # 扫默认范围，命中即退出 1
node scripts/check-public-artifacts.mjs --all  # 连第三方技能一起扫，作参考
```

它查七类：内网 IP、Windows 与家目录绝对路径、内部命名空间、内部项目名、内部技能名、内部命令名。

**局限写明**：`.xlsx`、`.docx` 这类压缩产物扫不到明文，只能靠它的生成器在扫描范围内间接把关。所以模板类产物必须由脚本生成、不许手改——这与 §6.7 的模板维护规则是同一个原因。

## 12 需要你拍板的六项（4、6 已定）

1. **目标用户**：半技术（会装软件、能读报错）／纯非技术。默认半技术，纯非技术留到 P2。
2. **交付边界**：到测试环境可演示 ／到生产。默认测试环境，上生产另立一票。
3. **首批项目类型**：中后台 CRUD ／含第三方集成。默认 CRUD 加一个文件上传，先不碰外部系统。
4. **宿主（已定）**：仅 DSH。不做 Qoder 兼容，省掉双宿主适配层（§15.10）。技能只按 DSH 的工具集设计：`ask_user_question`、`subagent`、`job_*`、文件与终端工具。
5. **部署环境**：能否连外网。默认能；不能则要预置离线依赖包与离线模板。
6. **执行引擎（已定）**：DSH 上是可选层，默认观察档，派发档需观察校准度不低于 80%（§15.3）。单票项目强制退回跟做档，不开引擎。

## 15 执行引擎：把 Super-agent 接进来

### 15.1 它是什么

Super-agent 是 DSH 团队公开的双层 Agent 架构（MIT 原型，另有可装在桌面版 DSH 上的 bundle 实现）。一句话：**把「收消息、判断、派活、干活、交付」拆成两层——Router 只做判断，不做技术决定；Worker 一单一会话一工作树**。

| 模块 | 干什么 | 补我们的哪个缺口 |
| --- | --- | --- |
| 触发器 | 聊天消息、issue、CI 失败、本地投递文件都是入口 | A0 收活不再只靠人开口 |
| 准入 | 先用规则零成本筛，再用模型判「够不够开工」 | 省 token 的第一道闸，也是 E1 的执行体 |
| 票 + 授权范围 | 决定接受即建单，附带不可变授权 | 我们的票缺「谁允许改到哪」 |
| Worker | 每单独立会话加独立 git 工作树 | A4 不再挤在一个上下文里 |
| 订阅直通 | 票认领后，该线程的消息直达 Worker | 补需求不用重走全流程 |
| 交付 | commit / patch / PR，默认不合并 | 正好接 A6 |
| 看门狗 | 查「多久没进展、是否死循环、是否跑偏」 | 我们缺可计算的判据 |
| 注意力闸门 | 只在三种情况打扰人 | P9 的执行体 |

它解决的是**并行与无人值守**，不解决**什么叫做完**。这两件事正好一人一半，见 15.7。

### 15.2 七个动作落到引擎实体上

| 动作 | 引擎里对应什么 | 谁做 |
| --- | --- | --- |
| 收活 | 触发器 | 事件源 |
| 校准 | 准入：规则快筛 → 模型慢筛 | Router |
| 切片 | 决定接受 → 一张或多张票，各带授权范围 | Router |
| 起架 | 准备命令加第一个执行尝试 | Worker |
| 逐单 | 一次执行尝试，结束时交报告 | Worker |
| 验收 | 报告「可复核」加结构化提问加人卡 | Worker → 人 |
| 交付 | commit / patch / PR，默认不合并 | Worker |

一句话：**七动作管「做什么、算不算完」，引擎管「谁在什么时候、用多大权限做完」。**

切片的规则不变：一张票一次上下文、做完能演示、阻塞边真实。引擎只是让每张票能同时开跑，不改变切法。共享契约变更仍然要单独出单、先做——工作树隔离的是文件，隔不开契约。

### 15.3 三种运行档

| 档 | 谁执行票 | 人什么时候出现 | 用在 |
| --- | --- | --- | --- |
| 跟做 | 同屏会话，现在的形态 | 每张票的关键判断 | 前 3 个项目、需求模糊、学习期 |
| 观察 | Worker 照跑，但只记录不交付 | 事后审它「本来会做什么」 | 换模板、换领域、开派发之前 |
| 派发 | Worker 后台并行 | 只在三种打扰许可时 | 票清晰、领域熟、批量小需求 |

升级条件写死，不靠感觉：**观察档跑满 10 张票，且「本来会接受的单子，人后来真接受」的比例不低于 80%**，才允许开派发。这个比例就是校准度，见 §9。

反过来，出现一次「跑偏没被拦住」，退回观察档，并把那次越界写成一条判据。

### 15.4 授权范围怎么落到票

票模板里加一行（§6.2 已加）：

```text
授权：业务方张三批准；可改 apps/web 与 packages/shared；
      不动契约字段、不加依赖、不改 CI；diff 超 200 行停下问
```

三条越界判据，都能算：

1. 改了授权目录之外的文件
2. 改了公共接口、新增依赖、改了 CI
3. 单张票 diff 超过 200 行（默认值，按项目可调）

命中任一条，Worker 停下来报「受阻」，不许自己解释成「顺手改的」。授权范围是**不可变**的：要扩大，重新出单，而不是在执行中改。

### 15.5 打扰协议

只有三种许可：

1. **结果可用**：可以被复核或直接用
2. **需要拍板**：一个具体问题加选项
3. **做不下去**：说清试过什么、缺什么前置

其余全部静默：进度只更新票，不发消息。硬限制：一次打扰不超过 100 字，问题不超过 30 字，报告摘要不超过 600 字。超了算 bug，不算风格。

反面清单（明确不许）：普通进度播报、模型重试通知、「PR 已开但还没做完」、重复报同一个里程碑、为常规步骤征询默认值。

### 15.6 看门狗三条判据

| 判据 | 怎么算 | 阈值 | 动作 |
| --- | --- | --- | --- |
| 无进展 | 距最近一次有意义信号（报告、输入被读、后台任务有输出）的时长 | 15 分钟警告 / 30 分钟停 | 先通知，再结束本次尝试，报「等待」 |
| 死循环 | 同一票连续以同一错误失败，或同一单反复退回重排 | 3 次 / 2 小时 | 停止重试，转人工，附上重复的错误行与已试过的补救 |
| 跑偏 | 命中 15.4 的三条越界判据 | 一次即报 | 立即停，报「受阻」，不自动改写代码 |

这三条替代原来那句「连续两次修复失败就停」——那句话没有执行体，现在有了。所有判据只用已存字段，重启后可重放；阈值写进配置，不写死在提示词里。

### 15.7 它没有、我们必须补的五样

1. 五要素规格书与元素编号（F-xx）
2. 验收谓词 3–5 条
3. 验收卡（人签）
4. 冷启动清单与 E2E 双模
5. 防假绿三条

换句话说：**引擎保证「有人在做、跑偏了会停」；我们保证「做完的东西是对的」。** 谁都不替谁。

### 15.8 不照抄的五样

1. **不把数据库当真相**。它的票状态在 SQLite 里，对非技术用户不可读。我们的票与证据仍是文件，库最多做索引。
2. **不开全权限当默认**。它的 Worker 以最高权限运行，隔离靠目录和提示词，它自己的文档也承认不是安全边界。我们的默认是观察档加交付 patch。
3. **不自动合并**。它默认也不合并，这条保持一致：合并永远是人签。
4. **不从自由文本推断「人在等回答」**。必须有结构化提问字段，否则宁可静默。
5. **不把阶段写进调度**。它的票有自己的阶段视图，那是给面板看的，不是调度依据；我们的调度仍靠依赖边与证据。

### 15.9 成本、风险与最小接入

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 并发 Worker | 3（上限 16） | 多开不等于快，合并冲突与 token 一起涨 |
| 每小时票 | 12 | 熔断，防失控 |
| 单票时长 | 30 分钟 | 到点结束本次尝试，报等待 |
| 每日 token | 首版只记录不封顶 | 先看基线，再定阈值 |
| 交付 | patch + PR 草稿 | 合并永远是人 |

**最小接入顺序**（以下只在 DSH 上做，不做全量）：

1. 只接一个本地投递目录当事件源，不接 GitHub、不接 CI
2. 准入规则只写三条：来源在白名单、消息不是机器人发的、同一线程已有票则跟进不新开
3. 只跑观察档，产出「本来会做什么」的清单给人看
4. 票与证据仍写 `.fde/`，不上库
5. 校准度达标后再开派发，同时上线看门狗与熔断

最大风险不是模型不行，是**人以为它在干活**。所以观察档必须真的只观察，界面上要一眼看出「这单还没人批」。

### 15.10 只支持 DSH：放弃兼容换来的三件事

不做 Qoder 兼容，省下的不是一点点：

1. **不用写宿主适配层**。技能只按 DSH 的工具集写（`ask_user_question`、`subagent`、`job_*`、文件与终端工具），不必为每个工具准备两套调用；§5.4 的卡、§6.2 的执行者、§7 的触发词都只写一遍。
2. **常驻可以真测**。零常驻、每轮问几项、钩子是否生效，都只需在一个宿主上实测，不必再做「取两宿主交集」的保守设计——v0.2 为了兼容把每轮压到 3 项，现在可以直接测出上限再定。
3. **环境门槛少一半**。用户只需装 DSH，不用管 Qoder 的目录约定、插件路径、双 home 同步。

代价是**单一宿主锁定**，这条要写明，不能装作没有：

- 一旦 DSH 不可用，交付链断在「执行」这一步，业务资产不断。
- 票、证据、四道阻断门、五要素规格书、验收卡都与宿主无关；迁移成本等于重写一个执行者适配层，不动业务资产。这叫「锁定但不封死」。
- 所以每季度做一次宿主无关性检查：随便挑一张票，只用票里的字段（不读 DSH 专有能力）把它做完。能做完，说明资产还是干净的。

**引擎仍然可选**，理由不是兼容而是成本：只有一张票的项目，开引擎的调度开销大于收益。默认跟做档，票多了再升——这条与「仅 DSH」无关，别混为一谈。
