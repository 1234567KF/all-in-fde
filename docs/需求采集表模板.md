# 需求采集表模板 v1.0

> 配套《all-in-fde 方案 v0.3》§6.7 与 §4.2 的 A1 校准。
>
> 空白模板：[需求采集表-空白模板.xlsx](../skills/all-in-fde/assets/需求采集表-空白模板.xlsx)（16 张表 + 说明页，含下拉与示例）。
> 生成器：`tools/build-requirement-template.py`。**改模板改脚本再重跑，不要手改 xlsx。**

---

## 1 它解决什么

人只会说一段话，AI 一动手就跑偏。中间缺一层**人能逐格核对的事实表**。

所以链路是三段：

```text
一段话 ──AI 填──▶ 需求采集表 ──人审定──▶ PRD 分卷 + 原型 ──▶ 票
  人写              AI 填、人核              AI 写、人看            AI 做
```

表是**事实**（有什么角色、页面、字段、规则、验收），PRD 是**裁决**（为什么这么做、冲突以谁为准），原型是**样子**（点下去发生什么）。三层各写各的，不许互相抄：PRD 引表编号，原型引页面 ID。

样例形态：16 张表 → 15 卷 PRD → 7 个原型页，页面 ID 与 S7 一一对应。

## 2 十六张表各答什么

| 表 | 一句话 | 主要列 | 编号前缀 | 谁审 |
| --- | --- | --- | --- | --- |
| S0 需求输入 | 客户原话与附件清单 | 类型、内容原文、来源 | `IN-` | 人（必审） |
| S1 项目基础 | 背景、目标、范围、里程碑 | 类别、内容、衡量标准 | `BG-` | 人（抽查） |
| S2 术语 | 客户黑话与易混词 | 术语、定义、同义词 | `T-` | 人（抽查） |
| S3 角色与隔离 | 谁能干什么、看到哪一层 | 职责、可见范围、敏感特权 | `R-` | 人（必审） |
| S4 页面权限矩阵 | 页面 × 角色，一格一结论 | 端/模块/页面ID + 角色列 | 无（用页面ID） | 人（抽查） |
| S5 业务主链 | 一步一行加旁路 | 触发、主责、产出、时限 | `M-` | 人（必审） |
| S6 状态机 | 一态一行，状态唯一定义处 | 进入条件、操作、下一状态 | `ST-` | 人（抽查） |
| S7 功能需求 | 一页一行，页面的全貌 | 结构/列表/操作/弹窗/规则/交互/异常 | `REQ-` | 人（必审） |
| S8 字段规格 | 跨页面共享字段字典 | 含义、必填、格式、敏感级 | `F-` | 人（抽查） |
| S9 数据实体 | 实体、关系、编号规则 | 属性、关系、编号规则 | `E` | 人（抽查） |
| S10 客户明确约束 | 技术要求的唯一入口 | 约束、验收口径、出处 | `NF-` | 人（抽查） |
| S11 验收AC | Given/When/Then 加数据断言 | 挂REQ、前提、动作、结果、数据断言 | `AC-` | 人（抽查） |
| S12 外部依赖边界 | 一期做到哪、不做什么 | 依赖方、做到哪、失败处理 | `EX-` | 人（抽查） |
| S13 疑问与备注 | 待拍板 + AI 假设登记 | 关联行、问题、建议、回答 | `Q-` | 人（必审） |
| S14 决议追踪 | 拍板记录 + 回写跟踪 | 结论、影响行、回写状态 | `R-` | 人（抽查） |
| S15 覆盖核对 | 原句逐句有着落 | 来源、应落表、实际落点 | `CV-` | 机器（必须全绿） |

**人只审五页**：S0（原话有没有被改）、S3（角色对不对）、S5（主链顺不顺）、S7（页面清单全不全）、S13（疑问有没有被藏起来）。其余抽查。目标：单项目审定 ≤30 分钟。

## 3 填写六条铁律

1. **S0 一字不改**。可以一句拆多行，不许润色、不许合并、不许「优化表达」。
2. **客户没说的写「待确认」**，并在 S13 登记一条疑问。**不许沉默假设**——AI 建议填在 S13 的「AI建议方案」列，不直接写进事实列。
3. **编号是承诺**。`REQ-` / `AC-` / `BR-` / `EB-` / `F-` / `E` / `ST-` 发布后不复用；删了留空号，不重排。
4. **每行能回指来源**：S0 编号或附件位置。指不到就是编的，删掉或进 S13。
5. **状态=未核验的行必须有对应疑问或说明**，否则视为未完成。
6. **形容词要能指到行为**。「操作便捷」不算，「主操作一步可达、列表默认按时间倒序」算。
7. **AC 必须带数据断言**。只写「操作成功」的 AC 不算验收项；金额到分、汇总等于明细合计、状态字段等于什么，至少写一条。

## 4 联动：三处引用 + 一条反向校验

### 4.1 表 → PRD

PRD 每个二级标题下写一行来源：

```markdown
### 3.2 审批生效

> 来源：S7 r12（A-CONTRACT-DETAIL）；S6 ST-C-02→03；S11 AC-C01/C02
```

PRD 里出现的每个页面 ID、实体编号、规则编号，都必须能在表里找到；找不到就是 PRD 自己发明的，退回改表。

### 4.2 表 → 原型

原型每个页面顶部写注释：

```html
<!-- 页面ID: A-CONTRACT-DETAIL | 来源: S7 r12 | 表版本: v1.0 -->
```

页面里的字段、按钮、空态、错误提示，与 S7 的 J（弹窗字段）、I（操作）、M（异常）逐项对应。**原型不发明字段**——需要新字段时先改 S7，再改原型。

### 4.3 表 → 票 → 验收

- 票的「本次让哪些从没有变能用」写 `REQ-` 编号（如 `REQ-C01`），不写「合同详情页」这种模糊指代。
- 票的验收谓词从 S11 取（如 `AC-C01`、`AC-C02`），不许现编。
- E6 冷启动的「核心旅程」取 S5 的前三步，不改写。

这条把「需求 → 票 → 验收」串成一条链：任何一条验收失败，能一路回溯到 S0 的哪句话。

### 4.4 反向校验（E4 契约门）

| 查什么 | 怎么查 | 不过怎么办 |
| --- | --- | --- |
| 表齐不齐 | 16 张表存在且非空（轻量档见 §5） | 补表 |
| 覆盖有没有缺口 | S15 每行「覆盖结论」为已覆盖 | 补行或记 S13 |
| PRD 能不能回溯 | 抽 PRD 全部编号，与表内编号集合求差 | 差集非空即退回 |
| 原型对不对得上 | 原型页面 ID 集合与 S7 D 列集合求差 | 差集非空即退回 |

这四项由脚本做，人工只看差集清单。

## 5 三档，别一刀切

| 档 | 表 | PRD | 原型 | 用在 |
| --- | --- | --- | --- | --- |
| **轻** | S0 / S1 / S3 / S5 / S7 / S11 | 3 卷：概览、页面、验收 | 可选，一个 HTML | ≤5 张票的内部小工具 |
| **标准** | 全 16 张 | 按业务域分卷 | 必做，页面 ID 对齐 | 客户交付（6–20 张票） |
| **重** | 全 16 张 + 端 × 角色矩阵细化 | 分卷 + 决议卷 + 差异清单 | 多端原型 | 多端、多角色、>20 张票 |

轻量档缺的表，在 S15 里登记「本档不适用」+ 理由，不算缺口。**不许默认走重档**——表填得再全，人审不动就是负担。

## 7 回写环

```text
PRD/原型生成时发现缺口 ──▶ S15 记缺口
        新问题        ──▶ S13 提问（带建议方案）
        人拍板        ──▶ S14 记决议 → 回写受影响行 → 回写状态列
        表更新        ──▶ 表版本 +0.1，PRD 分卷头部同步版本号
```

回写状态只有三个值：`已回写` / `部分回写` / `待回写`。**「部分回写」必须在备注里写还差哪行**，否则等于没回。

## 8 三处已知不足

诚实记下来，别假装完备：

1. **审计没有独立表**。审计要求散在 S10（约束）与 S7 K 列（留痕规则）里。参考脚手架自带审计内核，目前够用；等出现「哪些字段变更要留痕」的争议，再补一张 S16。
2. **模板不覆盖视觉规范**。颜色、间距、字体走 `DESIGN.md`，不在表里。
3. **S4 的角色列是动态的**。生成器先给 5 列占位，实际按 S3 的角色数增删列；不要用合并单元格。

- 改表结构：改 `tools/build-requirement-template.py` 的 `SHEETS`，重跑生成 xlsx，再同步本文件 §2 的清单。
- 加一张表：生成器加一项、本文加一行、方案 §6.7 的分档表加一列。

## 10 附录 A：PRD 分卷目录

表审定之后出 PRD。分卷不是为了好看，是为了让每卷能被单独读懂、单独改、单独被票引用。一份真实多端项目的 15 卷切法可以直接复用：

| 卷 | 内容 | 主要来自哪张表 |
| --- | --- | --- |
| 00a 关键决议与产品概览 | 产品定位、信息优先级、四项先行决议 | S1 + S14 |
| 00b 角色权限与账号规则 | 角色清单、权限码、账号与登录规则 | S3 + S4 |
| 01 业务流程与状态机 | 主链、旁路、状态流转 | S5 + S6 |
| 02 信息架构与交互规范 | 菜单树、页面 ID 清单、全局交互 | S7 前四列 |
| 03–07 管理端各域（系统管理 / 企业认证 / 检测审定发证 / 证后与码 / 计费审计） | 按业务域分的页面与规则 | S7 分组 + S11 |
| 08a–08b 企业门户 | 工作台与申报 / 证书与监督 | S7 分组 + S11 |
| 09 小程序与公众端 | 作业端、H5、扫码落地 | S7 分组 + S12 |
| 10 关键业务规则 | 跨页面的 IF-THEN、编号、计算口径 | S7 业务规则列 + S2 + S10 |
| 11 验收标准 | Given/When/Then 全集 | S11 |
| 12 交付差异与确认清单 | 与客户口径的差异、挂起项、待确认 | S12 + S14 + S13 |

三条写法要求，缺一条就不算合格分卷：

1. **00a 第一节写信息优先级**：业务规则与状态枚举以 PRD 为准、页面布局可参照原型、原型与 PRD 冲突以 PRD 为准。没有这句，后面所有冲突都要重新吵一遍。
2. **每卷二级标题下写来源行**：`> 来源：S7 r12；AC-C01/C02`。
3. **卷与卷不重复定义**：状态只在 01 定义、规则只在 10 定义、验收只在 11 定义，其余卷只引用。重复定义的那一份迟早会过期。

轻量档压缩成三卷：概览（00a+00b）、页面（02 + S7 分组）、验收（11）。压缩时保留 00a 的信息优先级那一段，别省。
