# ponytail 在 all-in-fde 里的用法

上游正文只说「怎么省」，不说「什么时候该省」。这一份补后半句，也是本仓库对它的唯一改动点。

## 什么时候加载

| 场景 | 是否加载 | 档位 |
| --- | --- | --- |
| A4 逐单，执行者开工第一件事 | 加载 | `full` |
| 用户说「精简点 / 少写点 / 别搞复杂」 | 加载 | 用户指定的档 |
| 需求本身可疑（做了没人用） | 加载并主动反驳 | `ultra` |
| A1 校准、A2 切片 | 不加载 | —— 那两步定「做什么」，不是「怎么写」 |
| 修数据、改配置、跑迁移、生成文档 | 不加载 | —— 不是写代码 |
| 脚手架 `gen:module` 生成 | 不加载 | —— 生成的 9 个文件是契约结构，不是过度设计 |

入口技能不常驻它，A4 的 reference 里写死一条「开工先加载 ponytail」，避免靠模型自觉想起来。

## 三档怎么选

- `full`：默认。按上游六条阶梯写最小完整改动。
- `lite`：用户已经给了明确方案，只是要更小的实现；点名更小的选项，让人选。
- `ultra`：需求本身站不住，允许在动手前反驳需求。用在试点期判断「这东西该不该做」。
- 关：非代码任务。

## 与门禁的优先级（重要）

ponytail 的「懒」作用在**怎么写**，不作用在**交付什么**。下面四类即使它说能省，也不许省：

1. 五要素规格书、元素编号（F-xx）、验收谓词
2. 权限校验、审计写入、业务不变量
3. 测试——上游自己也写了「非平凡逻辑要留一个小测试」
4. 架构门禁：AST 规则、450 行棘轮、`arch:check`

冲突时的写法：**门禁与规格书优先**，并在工单里记一行「因门禁保留 X」，让它进 retro，而不是悄悄消失。这一条防的是「用精简当借口，把该有的校验删掉」——上游的基准显示它能保住安全项，但删减边界只能由我们的门禁定义。

## 产出要带的两样

1. **结尾一到两行**：跳过了什么、没检查什么、用户要知道的风险。上游的硬要求，也是人验收卡里的判断依据。
2. **捷径注释**：有已知局限的捷径写成 `shortcut: <限制>, <何时升级>`。retro 时统一收集，进债务台账——否则「以后再补」等于永不补。

## 不适用

- PPT、文档、表格类产出（内容生产，不是代码）
- 需求还没定的时候（先 A1，再谈省）
- 跨模块宽重构（那是 expand–contract 的活，省不出收益，反而容易漏调用点）
